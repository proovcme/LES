# Память и рабочие файлы · кандидат 779

01.11.2026. Собственные payload/state в `work/native-779`, синтетические данные.
Корпус и назначения моделей владельца не менялись. В тестовом состоянии явно
назначена ранее разрешённая Qwen3.5:9b с контекстом 8192. Новых библиотек нет.

## Реализация

Схема инструмента, привязка к сохранённому диалогу, scope, policy, Unicode-окна,
пагинация и advisory-проекция USER.md/MEMORY.md теперь в Rust. Python — адаптер
существующего harness. Чтение использует writer lease и восстанавливает pending
после получения блокировки. Внешний редактор защищён проверкой ревизий, а не
заявленной ОС-песочницей. Delete сохраняет историю и per-project tombstone;
удалённый файл обнаруживается после нового разговора/перезапуска. Restore/export
сохраняют UTF-8 BOM/CRLF. Export требует текущую ревизию. Исходники и файлы памяти
через delete не удаляются. Закрытие редактора ждёт файловую операцию, повторная
мутация блокируется.

## Реальная Qwen

Первый прогон 778 прочитал USER.md, но save с пропущенным полем отказал с общим
AGENT_INVALID. Теперь ошибка называет поле, схема объясняет text/expected_revision.
Повтор 779 сохранил предпочтение с actor=agent и receipt; новый чат его вспомнил.

Первый файловый прогон выявил ложные заявления: edit/delete не вызывались.
Это сохранённый провал, не исправленный ручной записью. Каждый модельный шаг
теперь получает пакет текущего запроса с реальными receipts; прошлые ответы не
подтверждают текущих действий. После изменения/CAS-конфликта новое чтение того же
файла не блокируется как старый повтор. Без записей сервер сообщает «Изменений
в памяти и рабочих файлах нет», независимо от слов модели. Классификатора по
ключевым словам и подставных результатов нет. Все будущие галлюцинации этим
не исключены.

Повторный реальный прогон прошёл восемь проверок: USER.md после перезапуска;
память только своего проекта; воспоминание в новом чате; отсутствие утечки в
другой проект; создание файла с точным текстом (кириллица, японский, newline,
emoji); точечная замена с сохранением остального; фактическое удаление;
восстановление точных байтов до удаления. Доказательства: `qwen-report.json`,
первый `files-qwen-report.json` с провалом, итоговый `files-qwen-v2-report.json`.
Pass сравнивал реальные файлы/историю, не только текст ответа.
