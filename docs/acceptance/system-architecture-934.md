# ЛЕС Light. Аудит архитектуры и рабочих процессов

**Объект** — обычный Windows-кандидат 0.1.3, сборка 934, рабочее дерево поверх `27b7eac`. Проверены исходники, хеш запущенного API, поведение на синтетических папках и результаты прежних опытов с живой моделью. Последняя запись об установке пользователя относится к 928. В этом аудите использован отдельный стенд. [Версия](../../config/version.json) · [Журнал выпусков](../RELEASE_LEDGER.md) · [Данные проверок этого аудита](system-architecture-934-evidence.json)

**Вывод.** Архитектурная проблема сосредоточена на переходе от найденного документа к конкретному утверждению. ЛЕС умеет обнаружить файл, сохранить его версию, найти фрагмент и открыть ссылку. На воспроизведённом вопросе по таблице весь этот путь работал, однако программа одинаково приняла верное и подменённое количество. Замена векторной базы или увеличение окна модели оставят такой результат возможным. Есть и самостоятельные ошибки в интерфейсе и выпуске. Для каждой нужен свой ремонт.

## Как работает обычный вопрос по папке

Пользователь выбирает датасет и задаёт вопрос. Каталог определяет, какие документы входят в область. Поиск возвращает адресуемые выдержки. Сборщик укладывает их и служебные сообщения в окно выбранной модели. Модель формулирует ответ. API связывает упомянутые источники с разрешёнными адресами, сохраняет ход и отдаёт ответ интерфейсу. Для открытия оригинала нужны версия документа и подходящий локатор, например страница PDF или лист и строка Excel. Явный выбор отдельного файла сужает область. Для разговора по целой папке этот шаг необязателен. ## Где ломается и как это доказано

### 1. Высший приоритет. Табличная ячейка теряет свою роль по дороге в ответ

В синтетическом PDF строка `Alpha item` содержала единицу `pcs` и количество `17.25`. Стенд построил индекс папки, вызвал публичный чат и записал сообщение, фактически полученное провайдером. Искомое значение в нём было. В независимых сессиях модель-приёмник возвратила по очереди `17.25 pcs [Источник 1]` и `999 pcs [Источник 1]`. Оба раза API ответил 200 за один вызов, привязал источник 1 и записал `validation=not_performed`. Пример демонстрирует точно воспроизводимое свойство программы. Частоту фактических ошибок живой модели по нему определить нельзя. [Протокол с двумя ответами](system-architecture-934-evidence.json)

Штатный тест этой же границы упал во всех четырёх вариантах — обычный поиск и агент при двух возможностях провайдера. Провайдер со строгой схемой ожидал поле `response_format`, которое ЛЕС не передал. Исключение стенда API представил как ошибку связи. В двух остальных случаях идентификатор строки из ответа не был принят как цитата, в том числе после повтора. Геометрия страницы успешно прочиталась. Первое исправление должно пройти через штатный чат и обеспечить строке, столбцу, единице и значению общий адрес от чтения до выдачи. Для точного запроса ячейку может вывести сама программа. Если структура неоднозначна, пользователю можно показать страницу и явно обозначить неопределённость. [Тест](../../tests/test_light_native_pdf_layout.py) · [Обработка строк](../../api/src/chat/table_facts.rs) · [Ветвление чата](../../api/src/chat/runner.rs)

### 2. Высокий приоритет. Ответ по нескольким документам может подменить объект или редакцию

В прежнем опыте по папке обе характеристики и общее условие попали в окно. При переформулировке живая модель привязала требование к паспорту другого оборудования. В отдельном опыте с редакциями отменённый срок выдавался за действующий. Обе ссылки могли вести к подлинному тексту. Идентичность файла, дата загрузки и дата действия нормы отвечают на разные вопросы. Для заданного кода нужен точный поиск по коду, для исторического вопроса — установленный интервал действия, для составного ответа — привязка каждой цифры к запрошенному объекту. Если применимость неизвестна, это следует отразить в ответе. [Стенд по папке](folder-architecture-934.md) · [Опыты по редакциям](llamaindex-934/parts/README.md)

### 3. Высокий приоритет для выпуска. Квитанция кандидата пропускает четыре файла

У испытуемого API совпали SHA-256 бинарника и запись о нём. Отдельно проверили механизм сравнения с текущими исходниками. Для каждого встроенного JSON стенд по одному добавлял пробел к возвращаемым байтам в памяти. Содержимое репозитория оставалось прежним. Для включённых контрольных файлов отпечаток менялся. Для `chat-commands.json`, `dataset-reader-schema.json`, `document-review-tool.json` и `table-document-tool.json` он сохранился, хотя Rust встраивает эти файлы при компиляции. Поэтому при изменении одного такого файла проверка способна принять прежний бинарник за актуальный. [Расчёт отпечатка](../../tools/native_asset.py) · [Все входы и потребители](system-architecture-934-evidence.json)

Есть ещё разрыв между проверяемым и выпускаемым вариантом. Workflow проверки собирает API с `--edge`, workflow выпуска — в обычном варианте. В установочном сценарии проверяются запуск, доступность UI и сохранение сессии после обновления. Из этого нельзя вывести, что из тех же байтов прошёл путь «папка → индексация → вопрос → цитата → оригинал». Отдельная команда отката после первого переименования полагается на выполнение второго. Требуется испытание остановкой именно на откате. [CI проверки](../../.github/workflows/verify.yml) · [CI выпуска](../../.github/workflows/release.yml) · [Сценарий установленного кандидата](../../.github/scripts/check-installed-candidate.ps1) · [Код отката](../../installers/windows/light/package.ps1)

### 4. Локальная ошибка. Одна отправка может попасть в историю дважды

У API уже есть защита от повторов. Обычный потоковый клиент не передаёт ключ запроса чата. На одном публичном SSE-маршруте две отправки одинаковой команды `/help` без ключа создали записи 1 и 2. При повторе с одним ключом обе вернули запись 3. Модель не вызывалась. Исправление ограничено временем жизни ключа в UI. Для повтора прерванной отправки ключ сохраняется, для намеренного нового сообщения создаётся заново. Проверять следует с обрывом после сохранения на сервере и до получения финального события клиентом. [Клиент](../../desktop/light/frontend/src/lib/api.ts) · [Сервер](../../api/src/chat/http.rs) · [Результат повтора](system-architecture-934-evidence.json)

### 5. Эксплуатация. Папка перечитывается целиком, а допустимое окно модели описано неоднозначно

У наблюдателя стоимость спокойного обхода зависит от суммы размеров допустимых файлов. Для локального маленького набора это разумная цена обнаружения скрытой правки. Для большой сетевой папки пока нет измерения, оправдывающего такую частоту. Вариант для проверки — события файловой системы, очередь изменённых путей и периодическая полная сверка с хешированием. Периодическая сверка должна поймать пропущенное событие и изменение с прежними размером и временем. Нужно измерить байты чтения, задержку обнаружения и поведение при недоступной сетевой папке. [Реализация](../../api/src/intake.rs) · [Сценарий потери оригинала](../../tests/test_light_native_folder_watch.py)

В 239 из 250 сохранённых случаев расчёт профиля совпал полностью. В остальных 11 разошёлся только `input_token_limit`, в том числе 32 768 и 131 072. Следует решить, какое ограничение имеет приоритет при сочетании настроенного и заявленного окна, и сверить это с фактическим лимитом провайдера на границе запроса. Подгонка числа в тесте оставит вопрос открытым. Ещё два падения из прежнего полного прогона относятся к смене маршрута наблюдаемого файла в Python-адаптере и к коду завершения аварийного работника форматов. У них другие точки входа. [Профили](../../core/src/model_profile.rs) · [Прежний полный прогон](llamaindex-934/parts/README.md)

### 6. Python и лишние слои

Карта насчитывает 720 Python-файлов. 417 достижимы из перечисленных Python-точек входа, 5 отнесены к поддержке runtime, 291 к тестам и инструментам, 7 помечены как кандидаты в неиспользуемый код. Обычный установочный путь Windows запускает Rust API. В то же время Python действительно нужен средствам разработки, отдельным внешним навыкам и путям совместимости. Попадание файла в пакет отдельно проверяется сборщиком. [Карта достижимости](../CODE_RUNTIME_MAP.md) · [Состав пакета](../../tools/build_light_package.py)

Семь кандидатов в `proxy/services` — `active_state_service.py`, `asbuilt_ocr.py`, `checklist_template_importer.py`, `glossary_chat_service.py`, `scoped_rag_builder.py`, `table_detect.py`, `update_service.py`. У них есть взаимные зависимости. Например, `scoped_rag_builder` импортирует `active_state_service`, а часть имён встречается в реестрах строками. Порядок удаления — проверить потребителей и манифесты, убрать модуль из пробного пакета, запустить обычный Windows-клиент офлайн, внешний Python-навык и поддерживаемые точки совместимости.
