# LES RAG и Увязка — аудит перед интеграцией

## Что проверено

- LES: локальный `main` и GitHub `main` на `52464821`. В рабочем дереве есть отдельный незавершённый кандидат Edge и его приёмка. Он не входит в этот аудит как опубликованная функциональность. [LES](https://github.com/proovcme/LES/tree/52464821fce1c82f4380007ff8e9f8a2bc7f2fc6)
- Увязка: локальная база `1610314` с изменениями в рабочем дереве. `origin/main` и GitHub на `1253a25`. Разница коммитов — транспорт DWG (суррогаты UTF-16 и OLE), тест и документация. Маршруты `model_data` и выбор читателей сверены с обоими состояниями. [Увязка](https://github.com/proovcme/uvyazka/tree/1253a25e6084cd7ed406b9d9c7e5146c620b395f)
- Windows LES: штатная цепочка идёт от `desktop/light/src-tauri/src/launcher.rs` через `runtime/src/services.rs` с `--native-only` к `api/src/main.rs` и Svelte `/app/`. Форма `desktop/light/frontend/src/components/DataLibrary.svelte` вызывает `POST /api/rag/index-external`. Установленные `les-api.exe` и `qdrant.exe` запускались отдельно с тестовым состоянием. Рабочий GUI и состояние пользователя в приёмке не участвовали.
- Увязка: `pyproject.toml` → `src/uvyazka/cli.py` или `server.py` → `model_data_tools.py`. Локальная панель из `dashboard.py` маршрутизирует чтение в `model_data_http.py`. Оба интерфейса обращаются к одному `ModelData` с базой проекта. Проверка HTTP поднимала реальную локальную панель на временном проекте.

- Публичный README LES правильно показывает BM25, dense, RRF, дочитывание, роль Qdrant Server и отсутствие нативного реранкера. Из общей схемы не видно, что автоматический Push и постоянный Folder Watch ещё открыты.
- `docs/BACKLOG.md` LES описывает переходное состояние, включая ещё не переключённый основной чат, старый bootstrap и ряд почтовых форматов. Текущий Windows launcher, Svelte/API и `api/src/mail/` показывают более позднее состояние. Старые отчёты полезны как история проверок.
- Увязка описывает ограниченное покрытие прямого чтения. Действующий `ModelData` уже отдаёт структурированные значения с происхождением, но проектные HTTP/MCP-маршруты не подходят на роль независимого читателя. Часть локальной документации дополнена незакоммиченными изменениями. Исправление DWG в публичной ветке сверено отдельно.

## Проверки и порядок приёмки

При внедрении наблюдения отдельно проверить два случая. Сейчас успешный обход
пустой папки завершается `INTAKE_EMPTY`, поэтому watcher должен отличать его от
неполного обхода и недоступности корня. Плановая сверка должна учитывать допуск
к отправке источников назначенному эмбеддеру. Выбор удалённой модели сам по
себе не даёт нового разрешения на фоновую передачу документов.

1. **Исходный путь.** 19 целевых проверок LES прошли с установленным нативным API и Qdrant Server на временном состоянии. В том числе очередь, допуск модели, физические страницы PDF, неизменность исходников и возобновление партии после завершения процесса. Генеративная модель не участвовала, эмбеддинги предоставляла локальная тестовая заглушка. Увязка — 10 тестов `test_model_data.py` и 4 теста DWG-транспорта прошли, включая локальную HTTP-панель, источники, частичное покрытие и точные ID. Инженерная приёмка на рабочем корпусе не проводилась.
2. **Этап 1.** Принять на изолированном установленном Windows: изменения при открытом и закрытом LES, байты с прежними размером/mtime, запись в процессе, недоступность реального SMB и неполный обход, принудительный обрыв на публикации, продолжение после запуска, видимость прежнего поколения и явная очистка. Отдельно замерить I/O при сверке большого корня. Повторное хеширование читает байты, поэтому частоту полных сверок надо измерить; парсинг и эмбеддинги для неизменившегося файла повторяться не должны.
3. **Этап 2.** Принять Push без tools, Pull, Hybrid и обычный чат без источников. На одних вопросах измерять поиск, вызовы инструментов, доставку доказательств и итоговый ответ. Проверить, что реранкер отключается, длинный документ ограничен, а лаборатория показывает причину исключения.
4. **Этап 3.** Принять версионированный `uvyazka-reader` для RVT/IFC/DWG с ограниченным JSONL, ожидаемым SHA, точным источником, покрытием, итоговой квитанцией и тестами отказов. Показать работу обоих продуктов по отдельности. Лицензирование пакета проверить до поставки.
5. **Этапы 4–6.** Подключить снимки к штатному журналу индексации. Отдельно принять точный фильтр с единицами, поиск обозначений и отношения, затем спорные соответствия и устаревание, затем переход к правильной редакции и элементу. В смешанном наборе PDF/XLSX/RVT/DWG/IFC сохранить оба исходных значения при расхождении. При неполном чтении результат «элемент не найден» не означает его отсутствия.

Этап 0 завершён. Переход к следующему этапу после Folder Watch зависит от его приёмки на отдельном состоянии.

## Первая правка этапа 1 — сверка содержимого

- Изменены `api/src/intake.rs`, `core/src/catalog/intake.rs`, `core/src/lib.rs` и сценарий `tests/test_light_native_intake_execution.py`. Повторное подключение считывает SHA-256 в фоне и сравнивает его с опубликованным хешем. При одинаковых байтах, размере и пути новая дата обновляет метаданные. Формат базы и контракт векторов прежние.
- На установленном API исходный тест воспроизвёл пропуск изменений при неизменных размере и mtime. На собранном кандидате 22 целевых теста прошли. Сценарий с новым и существующим индексом прошёл на Qdrant Server и Edge. Индекс хранил прежний SHA во время обработки новой редакции. После обрыва API на эмбеддингах задание продолжилось, и индекс получил новый SHA. Смена только даты не потребовала повторного вызова эмбеддера. Использовались изолированные данные и локальная модельная заглушка.
- `make verify` успешно собрал 2048 тестов. `make test` завершился с результатом 2046 успешно и 2 пропущено. Нативный запуск Svelte отдельно проверен в автоматическом сценарии с временным состоянием.
- Следующая часть этапа 1 — долговечный реестр корней и сверка после запуска, раздельные статусы файла и папки, защита от неполного обхода, проверка стабильности записи и приёмка с реальным SMB. Ещё предстоит проверить обрыв непосредственно на публикации и работу всего сценария из отдельного установленного приложения. До приёмки этапа 1 изменения в чат, модели и инженерные читатели не вносились.
