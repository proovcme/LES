# Аудит LES RAG 0.1.3, сборка 928

20 ноября 2026 года. Проверена ветка `codex/prealpha-0.1.3`, коммит `dab36e4`, вместе с локальными изменениями. В репозитории 1 470 отслеживаемых файлов, включая 715 Python и 345 Rust. По всему Python проверены синтаксис и статические импорты. Ручной разбор и сквозные проверки сосредоточены на пути от документа до ответа, ссылки и оригинала.

**Основные потери происходят при формировании ответа и при дочитывании.** Воспроизведены выдача другого документа по точному ID, исчезновение нуля и логического «ложь», отказ второй страницы Excel и исключение одного из трёх названных источников из первого запроса к модели. Для воспроизведения использованы временные файлы, отдельная база, локальный Qdrant и управляемые ответы модели. SHA-256 исполняемого файла API стенда совпал с SHA-256 API работающей установки.

## P1. Ошибки, меняющие содержимое ответа или останавливающие чтение

### 1. Поиск по ID документа возвращает одноимённый файл другого набора

В два тестовых набора помещены разные файлы с одинаковым относительным путём `register/common.txt`. В `search_sources` переданы ID документа из набора A, оба разрешённых набора и запрос о значении из B. Ответ HTTP 200 содержал сначала документ B, затем A. После проверки ID поиск сохраняет только имя файла и продолжает искать по всем наборам запроса. Область доступа пользователя соблюдена, идентичность выбранного оригинала потеряна. В текущем рабочем корпусе один пользовательский набор. Исправление проверяется тем же запросом с ожиданием, что каждый источник принадлежит выбранному документу. [Разрешение ID](../../api/src/chat/tools/sources/retrieval.rs#L436) · [Фильтр поискового запроса](../../api/src/chat/tools/sources/retrieval.rs#L472)

### 2. Точное чтение Excel теряет числовой ноль и значение False

В исходной строке были `Code=PUMP`, `Quantity=0`, `Enabled=False`. Поисковый узел сохранил оба значения. Вызов `read_excel_source` по физическому адресу вернул HTTP 200 и только `Code: PUMP`. Другая строка, состоящая из нуля и False, вернула HTTP 503 `CONTEXT_REQUIRED_SECTION_OVERFLOW`. При подготовке «точных» ячеек фильтр считает оба значения отсутствующими. Пустой результат затем выглядит для механизма разбивки на страницы как превышение бюджета. Проверка исправления должна различать пустую ячейку, ноль и False на всём пути до ответа инструмента. Сохранённые в Parquet значения позволяют исправить чтение без пересчёта эмбеддингов в воспроизведённом случае. [Определение присутствия](../../core/src/tables/mod.rs#L73) · [Отбор точных ячеек](../../core/src/tables/normalize.rs#L265) · [Проверка страницы](../../api/src/chat/tools/sources/retrieval/pagination.rs#L12)

### 3. Публичный Excel-читатель отклоняет собственное продолжение

Запрошены строки 2–4 одного листа с `limit=1`. Первая страница вернула HTTP 200 и готовые аргументы `continuation`, включая `offset`, хеш оригинала и хеш Parquet. Их повторная отправка без изменений вернула HTTP 422 `SOURCE_CONTINUATION_REVISION_REQUIRED`. Публичный вход требует ещё и `index_revision`. Исключение для закреплённого снимка предусмотрено для `read_source`, хотя Excel-читатель тоже закрепляет снимок и проверяет его. Это воспроизведено через API, на который направляет вызовы нативный MCP. Критерий исправления — пройти несколько страниц возвращёнными аргументами и отдельно проверить отказ при смене снимка. [Формирование продолжения](../../api/src/chat/tools/sources/workbook.rs#L274) · [Проверка на входе](../../api/src/chat/sources_api.rs#L51) · [Маршрут MCP](../../runtime/src/cli/mcp_tools.rs#L270)

### 4. Hybrid убирает третий явно названный документ до вызова модели

В наборе три файла с тремя разными контрольными фактами. Вопрос запрашивает давление в `A-1` и `B-2` и оговорку из `Notes.txt`. Поиск нашёл три файла. В первом сообщении модели присутствовали факты A и B, факт из Notes отсутствовал. При обычном ответе со ссылкой сервер завершил ход с HTTP 200 и `prefetch_complete=true`. При явном сигнале нехватки доказательств сервер сделал второй вызов и передал уже все три факта. Контрольный запрос без обозначений A-1 и B-2 получил три факта с первого раза.

Причина — выделение имён с буквой, цифрой и разделителем. Совпадения двух обозначений достаточно, чтобы сократить подборку, убрать навигационные карточки и затем проверить полноту относительно уже сокращённого списка. Инструменты дочитывания при первом вызове оставались доступны. Исправление должно сохранять покрытие явно названных файлов, включая обычные имена, и учитывать его при разрешении завершить ход. [Распознавание обозначений](../../api/src/chat/inspection.rs#L63) · [Отбор фрагментов](../../api/src/chat/evidence.rs#L1063) · [Проверка доставки](../../api/src/chat/runner.rs#L500) · [Решение о повторном чтении](../../api/src/chat/runner.rs#L703)

### 5. Математический интервал принимается за ссылки и срывает ответ

Нативный разборщик превратил `Диапазон параметра [0, 10] допустим` в текст с двумя метками источников и зарегистрировал номера 0 и 10 как неизвестные. Через штатный чат модель дважды вернула предложение с интервалом **и отдельной действительной ссылкой**. Итог — HTTP 503 `SOURCE_CITATION_MISSING`. Даже источник 10, реально присутствующий в окне, не делает ноль ссылкой. Нужны отдельные случаи для интервала, массива, одиночной короткой ссылки и явного списка `[Источники 1, 2]`. [Грамматика ссылок](../../core/src/citations.rs#L7) · [Нормализация чисел](../../core/src/citations.rs#L161) · [Отклонение ответа](../../api/src/chat/runner.rs#L808)

### 6. Интерфейс меняет правильный номер строки в тексте ответа

Проверен реальный обработчик отображения ответа. С источником на строку 18 он превратил «Запрошенный адрес (лист Register, строка 8) пуст. Значение найдено ниже [Источник 1]» в «…строка 18) пуст…». Один абзац и одна ссылка не гарантируют, что каждое упоминание строки относится к этой ссылке. Подмена происходит при показе, поэтому тот же эффект возникает при открытии истории. Проверенный адрес стоит показывать на кнопке ссылки, сохраняя числа в самом ответе. [Замена текста](../../desktop/light/frontend/src/lib/markdown.ts#L18) · [Отображение адреса ссылки в 930](../../desktop/light/frontend/src/lib/markdown.ts#L59)

## Что подтвердили проверки

- `make verify` прошёл. Сверены версия, карта Python, контракт API из 269 пар метод/маршрут. Собрано 2 245 тестов штатного набора. Форматирование проверено во всех шести Rust-проектах. В интерфейсе 65 тестов прошли, проверка Svelte не выдала ошибок и предупреждений.
- В первом `make test` прошли 1 888 тестов, упали 47, пропущены 310. Нативное ядро было подключено, исполняемые файлы отдельных служб в этом прогоне не задавались. При повторе 47 падений с путями к нативным компонентам и рабочим Python-окружением прошёл 41 тест. Оставшиеся шесть разобраны ниже. Отдельный почтовый набор дал 65 пройденных и один пропуск.
- Три проверки аварийного восстановления запускают дочерний Python с фиксированным путём `.venv/Lib/site-packages`. Во всех трёх дочерних журналах — `ModuleNotFoundError: pytest`. Среда с зависимостями в этой копии размещена в другом каталоге. Эти прогоны не дошли до проверки восстановления. [Подготовка документов](../../tests/test_light_native_document_nodes.py#L201) · [Пакетная индексация](../../tests/test_light_native_index_batch.py#L232)

Через нативную обёртку виртуальное окружение дало 0 в пяти попытках из пяти, базовый Python — 37 в пяти из пяти. Статус сбоя сохранился в обоих случаях. Ветвь обработки ошибки закрывает объект управления процессами и вызывает принудительное завершение до извлечения кода.
