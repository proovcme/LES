# Локальное обновление Windows 765–769

Проверено 31 октября 2026 года. Runtime установлен поверх 757 отдельными
порциями с контрольными суммами, резервными копиями SQLite и прежних файлов.
Откат каждой порции воспроизведён на одноразовой копии; контрольный файл
состояния сохранился. Это локальный патч, не новый установщик или публичный выпуск.
Нативные оболочка и Qdrant, встроенный Python и зависимости не заменялись.

По явному выбору пользователя ответы назначены локальной Qwen3.5:9b в Ollama,
контекст — 8192. Привязка BGE-M3 для поиска сохранена; просроченная проверка
возможностей повторена. Модели и пакеты не скачивались. Исходный .env
сверяется по SHA-256 без публикации содержимого.

## Исправления, обнаруженные при установке

В 766 устранён HTTP 400 при продолжении native chat: каноническая JSON-строка
arguments преобразуется в объект только на границе native-протокола.
Исходная история и OpenAI-ветка сохраняются. Некорректные аргументы отклоняются.
Минимальное воспроизведение давало 400 со строкой и 200 с объектом.
Capability probe теперь передаёт заданный num_ctx вместо значения сервера.

В 767 проверка документов разрешает точный task_id только внутри владельца.
Фактические счётчики журнала попадают в обязательный контекст до генерации.
Незавершённое или устаревшее задание получает независимое уведомление:
свободный текст модели не создаёт сохранённые выводы.

В 768 убрано затирание инструкции выбора инструментов обычным промптом чата.
Выбранный профиль сохраняется целиком; инструкция отличает ответ по имеющемуся
тексту от явно запрошенного действия. Это не заставляет модель выполнять
предметные решения и не гарантирует её надёжность.

Живой запрос также выявил SECTION_SCOPE_MISMATCH: weak retry вызывал плоский
hybrid без фильтра доказательств и возвращал навигацию. Повтор теперь использует
тот же маршрут, что первый поиск: иерархический либо плоский с evidence-фильтром.
Две регрессии проверяют оба режима и сохранение области документов.
После исправления тот же сценарий дошёл до модели без прежнего отказа.

В инструменте установки macOS добавлен ограниченный повтор rename только для
WinError 5/32: полный gate на Windows воспроизводил временную блокировку файла.
Каждая попытка заново проверяет отсутствие целевого приложения. Постоянный
отказ остаётся ошибкой; старое приложение не удаляется. Три проверки покрывают
временный/постоянный отказ и появление цели во время ожидания. Это не приёмка macOS.

При очистке собственного тестового набора обнаружен отдельный дефект удаления:
путь проверялся после очистки индекса и каталога. Windows возвращала физический
путь перенаправленного каталога, и поздняя проверка ошибочно отклоняла его.
Тестовый каталог уже был удалён; его оригинал сохранился. В 769 граница проверяется
до изменений, перенаправление допускается только по samefile родителя и корня,
а каталог удаляется после успешного переноса файлов в recovery. Четыре новые
регрессии проверяют небезопасный ID, выход из области, алиас и отказ переноса.
Это воспроизведённый дефект; причина всех прежних расхождений точек им не доказана.
На новом вымышленном наборе установленный 769 подтвердил INDEXED и целостность,
затем обычное удаление с обязательным recovery: 1 точка → 0, оригинал перенесён
в резервную папку. Оставшаяся папка первого теста отдельно сохранена вне рабочего
корпуса; пользовательские наборы не удалялись.

## Что подтверждено установленным приложением

- Запуск собственного launcher/API/UI/Qdrant, действительные readiness/instance
  и HTTP 200 основных API. Последние запуски служб занимали 6,4–7,2 с;
  это отдельные локальные замеры, не доказанное ускорение холодного старта.
- Обычный потоковый чат Qwen завершился примерно за 11 с. При исходном контексте
  32768 нехватка RAM вернула понятный CHAT_MEMORY_PRESSURE за 0,07 с.
  Порог 4 ГБ не снижался. Обнаруженный llama-server принадлежал самой Ollama;
  сторонние процессы не завершались.
- На вымышленном документе найдены срок 14 дней и исключение; ответ содержит
  обе буквальные цитаты. Оригинал по ссылке совпал с исходными байтами.
  Один из последних ответов занял 15,3 с, поиск — 3,5 с. Малый пример не заменяет
  независимые 100 вопросов или нагрузочную проверку реального корпуса.
- Реальная модель создала очередь document_review; отдельный read доставил
  документ. При отсутствии record SQLite сохранил pending после перезапуска.
- Прикреплённый XLSX, лист с пробелами: модель действительно вызвала read_window
  и верно назвала числовой ноль в B2. Это чтение, не проверка всей таблицы.
- В отдельном состоянии встроенные Python и нативный Qdrant проверили сохранение,
  возобновление, отклонение чужого владельца, транзитивное устаревание при замене
  байтов с сохранением размера/mtime, историю и курсоры Unicode-ячейки.
  Доставка модели в этой технической проверке имитировалась; смысловая точность
  и исполнение реальной моделью этим результатом не подтверждаются.

## Что остаётся открытым

Qwen9B несколько раз ответила «сохранено/reviewed», не вызвав record, в том числе
после отдельного read. В базе нет соответствующих review_events; независимое
уведомление сообщает 0 из 1. Исправление инструкции не закрыло эту ненадёжность.
Автоматическое многошаговое завершение проверки реальной моделью не принято.
Нельзя скрывать этот провал зелёными тестами или подставлять выводы вместо модели.

Вопрос о хвосте длинной XLSX-ячейки завершился частичным ответом:
UPSTREAM_RESPONSE_INVALID, completion_status=interrupted и STREAM_INTERRUPTED.
Контрольный хвост не получен. Сам адресный reader проверен отдельно, но полный
модельный путь длинной ячейки остаётся открытым. Стенд должен считать partial
ошибкой приёмки, даже если SSE содержит событие final; эта проверка добавлена
в локальный стенд. Прежний провал сохранён, успешный повтор не заявлен.

В ранних полных прогонах наблюдалось расхождение каталога и native-точек
вымышленного документа; исправлялся только этот набор. Причина не установлена.
Изолированные записи, копия хранилища и последующие последовательные перезапуски
сохраняли точки; контрольное завершение API/UI и restart Qdrant дали 2/2/2.
Это не доказательство целостности всего пользовательского корпуса.

Первый стенд ошибочно находил старую задачу по одинаковому вопросу из другого
чата. Исправлен выбор ID из результата инструмента с проверкой его записи.
После этого сохранён и отдельно описан действительный провал record.
Отсутствующий Idempotency-Key при первой загрузке XLSX также исправлен в стенде.

Геометрия нативного окна, экранный диктор, все клики, чистая Windows и новый
полный установщик не проверены. Computer Use не применялся.
Установленное окно 769 открыто обычной оболочкой: desktop сообщает loaded,
launcher — ready, instance API и UI отвечают 200. Это не визуальная проверка.
Контрольные суммы всех установленных порций совпали; SHA-256 .env не изменился.
