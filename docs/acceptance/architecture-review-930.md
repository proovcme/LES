# Архитектурный аудит LES RAG 930 и план стабилизации

21 ноября 2026 года. Проверен исходный код Windows-кандидата 0.1.3 на коммите `27b7eac`. Цель — установить, кто принимает решения на пути от выбора папки и модели до сохранённого ответа и открытия оригинала. Отдельно проверены повтор запроса, отсутствие файла и неполная конфигурация индекса.

**Вывод.** У запуска приложения, назначения модели и публикации файла в индекс есть конкретные владельцы. Наиболее дорогие расхождения возникают там, где клиент и сервер по-разному решают, можно ли выполнить запрос, а внутри сервера — где признаки поисковой выдачи принимаются за признаки пользовательского задания. Ниже приведены входные данные, фактическое поведение и место, в котором можно исправить каждое расхождение.

**Решение для разработки.** Первым изменением я бы сделал воспроизводимым один запрос от выбора папки до перехода по ссылке. Сейчас точный путь может превратиться в имя файла, имя проверяется только среди найденных кандидатов, а успешное попадание кандидата в контекст ещё не означает, что в нём есть нужная оговорка. На всех трёх переходах можно потерять смысл до генерации. Доставка факта, выбор источника, обработка повтора и открытие оригинала поддаются точной проверке на управляемом ответе. Верность вывода по прочитанному требует отдельной проверки с живой моделью. ## Расхождения, которые удалось проверить

### 1. Источники сохранены у диалога, но их должен повторить клиент

В базе у сессии есть `scope_json`. Окно при каждой отправке снова передаёт область, принудительно задаёт `hybrid` и переводит роль `agent` в режим `search`, если выбраны документы. Сервер загружает сессию, но список наборов для ответа строит из тела запроса. При включённой области умолчание сервера для способа поиска — `pull`. Поэтому одного ID зарегистрированного диалога недостаточно, чтобы воспроизвести отправку из окна. [Хранение](../../core/src/workspace/writes.rs#L213) · [Решение клиента](../../desktop/light/frontend/src/lib/workspace.svelte.ts#L296) · [Загрузка сессии и области](../../api/src/chat/prepare.rs#L211) · [Умолчание сервера](../../api/src/chat/runner.rs#L44)

В изолированной сессии через API сохранена область с одним набором. В отдельном запуске подлинной Rust-функции разрешения области вход с одним `session_id` дал `default_none`, поиск по документам выключен. Явная передача того же набора дала один разрешённый ID и включила поиск. Есть и расхождение в обработке устаревшего выбора. На входе с существующим и отсутствующим наборами функция чата сохранила первый и записала предупреждение. Публичный инструмент поиска с той же парой вернул 403. Подготовка чата останавливается при полностью пустой области. Опечатка в типе области даёт предупреждение и выключает поиск. Сквозной генерации для этих примеров не выполнялось. [Разрешение области](../../core/src/chat_request/scope.rs#L29) · [Проверка результата в чате](../../api/src/chat/prepare.rs#L275) · [Проверка инструмента](../../api/src/chat/sources_api.rs#L104)

**Изменение.** Разрешать намерение пользователя один раз на сервере. Запрос без области может наследовать выбор зарегистрированной сессии, явный `none` должен его выключать. Для старых клиентов потребуется сохранить документированные умолчания или версионировать переход. Для частично недействительного выбора нужно одно явное поведение в чате и инструментах.

### 2. Полнота ответа считается относительно того, что уже нашёл поиск

Hybrid формирует список ожидаемых документов из `candidate_documents` первичной выдачи. Список ограничен 64 карточками. У карточки есть полный относительный путь и отдельно последнее имя файла. Сопоставление с вопросом читает только последнее имя. Затем по полученному множеству ID сокращается подборка и проверяется, все ли ожидаемые ID вошли в окно модели. [Сбор карточек](../../api/src/chat/tools/sources/retrieval.rs#L515) · [Путь и последнее имя](../../api/src/chat/tools/sources/retrieval.rs#L529) · [Распознавание](../../api/src/chat/inspection.rs#L75) · [Отбор](../../api/src/chat/evidence.rs#L1064) · [Проверка полноты](../../api/src/chat/runner.rs#L507)

Проверка функции из 930 с вопросом `Read A-1, B-2 and current/Notes.txt` дала следующие множества.

| Карточки на входе | ID, которые функция сочла названными |
| --- | --- |
| A, B и единственный `current/Notes.txt` | A, B, current |
| Те же карточки плюс `archive/Notes.txt` | A, B, current, **archive** |
| Только A и B при том же вопросе | A, B |

В этом опыте измерялось множество документов на выходе распознавания. Исправление 930 для трёх уникальных имён остаётся подтверждённым. **Архитектурное ограничение** в том, что документ, выпавший до распознавания, не попадает в список ожидаемых. Такой проверкой нельзя доказать покрытие пользовательского запроса.

**Изменение.** Явно выбранные документы передавать по ID. Упомянутый в вопросе полный путь разрешать по каталогу выбранной области с учётом папки. Различать названные, найденные, переданные модели и процитированные документы. Для свободного смыслового запроса точный перечень ожидаемых файлов заранее неизвестен.

### 3. Экран готовности и поиск проверяют разные свойства индекса

Нативный `/api/health` проверяет ответ хранилища, общее число точек, отсутствие известной ошибки восстановления и совпадение имени коллекции в файле конфигурации. Настоящий поиск дополнительно разрешает конфигурацию, токенизатор при необходимости и соответствие назначенной модели модели индекса. В интерфейсе ошибка чтения реестра моделей превращается в `null`. Это позволяет показать «Поиск доступен», хотя назначение модели проверить не удалось. [Проверка состояния](../../api/src/status.rs#L93) · [Условия поиска](../../api/src/chat/tools/sources/retrieval.rs#L145) · [Обработка ошибки реестра](../../desktop/light/frontend/src/components/StatusPage.svelte#L44) · [Подпись в интерфейсе](../../desktop/light/frontend/src/lib/system-status.ts#L32)

На изолированном API 930 тестовое хранилище сообщало 10 точек. Файл конфигурации содержал только правильное имя коллекции. Ответ состояния — `ok / ready / dense_available=true`. Публичный вызов поиска в том же процессе — HTTP 503 `INDEX_NOT_CONFIGURED`. При отдельной проверке интерфейс показал «Поиск доступен» с таким же положительным состоянием хранилища и недоступным реестром. При успешно прочитанном реестре без назначения он показал «Нужна настройка».

**Изменение.** Выделить общую проверку возможности начать поиск. Экран может вызвать её без генерации вектора и без обращения к модели. Состояния «хранилище отвечает», «поиск сконфигурирован» и «проверка не удалась» должны иметь разные результаты.

### 4. Окно теряет идентичность отправки при обрыве

Сервер сначала сохраняет результат, затем отправляет финальное событие в окно. Повтор с тем же ключом может вернуть уже сохранённый результат. При обрыве до финального события клиент восстанавливает текст вопроса, но не сохраняет и не отправляет ключ этой попытки. В итоге для сервера повтор совпадает с сознательной второй отправкой того же текста. У черновиков в этом же приложении подтверждение потерянного ответа уже предусмотрено. [Приём ключа](../../api/src/chat/http.rs#L174) · [Запись и отправка результата](../../api/src/chat/http.rs#L94) · [Поиск существующей записи](../../core/src/chat_request/journal.rs#L68) · [Запрос из окна](../../desktop/light/frontend/src/lib/api.ts#L63) · [Восстановление вопроса](../../desktop/light/frontend/src/lib/workspace.svelte.ts#L336) · [Черновики](../../desktop/light/frontend/src/lib/drafts.ts#L18)

В проверке реального кода окна после потери финального события две отправки имели одинаковое тело и обе ушли без ключа. На нативном API две одинаковые команды без ключа получили ID истории **1 и 2**. Две команды с одним ключом получили **3 и 3**. Команда исполнялась без модели. Сценарий потери финального события и поведение хранилища проверены раздельно.

**Изменение.** Выдавать ключ при отправке вопроса, сохранять его для восстановления этой попытки. Новая сознательная отправка получает новый ключ. Отдельно обработать случаи, когда прежний ход ещё выполняется, завершился или был прерван.

### 5. Клиент блокирует локальную справку из-за отсутствия модели

В окне проверка назначения модели выполняется до отправки любого текста. На сервере команды справки исполняются до выбора модели. При пустых ролях один и тот же ввод `/команды` в проверке окна дал сообщение о неназначенной модели и ноль HTTP-запросов. У нативного API и JSON, и потоковый вызов вернули справку, число обращений к модели — ноль. [Решение окна](../../desktop/light/frontend/src/lib/workspace.svelte.ts#L277) · [Решение сервера](../../api/src/chat/runner.rs#L24) · [Встроенные команды](../../core/src/chat_commands.rs#L26)

**Изменение.** Передавать вопрос серверу, который уже различает команду и генерацию. Если для доступности кнопки нужен предварительный результат, его должен давать тот же классификатор.

### 6. У документа есть две полезные характеристики, но каталог показывает только одну

Наблюдатель сохраняет последний индекс, если файл исчез. Это осознанное решение, полезное для временно отключённого диска. Наблюдатель выдаёт присутствие файла, а библиотека читает только статус индексации. [Решение о сохранении](../modules/native-folder-watch.md#L25) · [Статус наблюдения](../../core/src/catalog/intake/watch.rs#L295) · [Статус библиотеки](../../core/src/catalog/library.rs#L137)

На тестовой базе, соответствующей этим состояниям, получены ответы трёх публичных маршрутов. До перемещения файла библиотека и наблюдатель дали `INDEXED`, оригинал открылся с HTTP 200. После перемещения и установки признака отсутствия библиотека по-прежнему дала `INDEXED, 1 фрагмент`, наблюдатель — `MISSING`, открытие оригинала — 503 `SOURCE_UNAVAILABLE`. Метку отсутствия в этом опыте задали в тестовой базе. Отдельный штатный сценарий в репозитории проверяет её появление после обхода и сохранение прежних векторов. [Открытие оригинала](../../api/src/documents.rs#L175) · [Штатный сценарий наблюдения](../../tests/test_light_native_folder_watch.py#L268)

**Изменение.** Показывать вместе редакцию сохранённого индекса и доступность оригинала по последнему наблюдению. Это позволяет сохранить возможность искать по снимку и сразу объяснить, почему исходник сейчас не откроется.

### 7. При втором сжатии памяти фраза может потерять автора и условие

Входом было одно сообщение пользователя из двух абзацев, «Срок согласован.» и «Только при получении разрешения.». При первом сжатии выбор записи 0 сохранил всё сообщение с подписью пользователя. При следующем сжатии функция разделила прежнюю сводку по пустым строкам. Теперь запись 0 содержала только утверждение о согласовании, а запись 1 — оговорку без автора. Выбор записи 1 прошёл проверку и сохранил отдельное «Только при получении разрешения.». Выбор записи 0 оставляет утверждение без оговорки. Для воспроизведения использованы две последовательные операции планирования и выбора, скомпилированные из исходника 930. Индексы выбора задавал стенд. Это проверяет допустимый результат работы программы. Частоту такого выбора живой моделью предстоит измерить. [Подготовка записей](../../core/src/conversation_summary/mod.rs#L99) · [Сохранение выбора](../../core/src/conversation_summary/mod.rs#L130) · [Вызов в приложении](../../api/src/conversation/mod.rs#L98)

### 8. Один длинный ход блокирует сводку последующих коротких ходов

В окне модели на 24 000 токенов первому ходу задали вопрос из 12 001 символа, за ним разместили короткое решение. Планировщик вернул `SUMMARY_TURN_TOO_LARGE`. После добавления ещё одного короткого решения получили ту же ошибку. В коде собственный предел пакета составляет 12 000 символов вместе с оформлением. При такой ошибке обработчик сохраняет текст ошибки и оставляет позицию чтения прежней. Следующая попытка начинает с того же хода. Исходная история сохраняется. Для человека это означает, что последующие решения не попадут в обновлённую сводку при повторе с тем же состоянием. Проверены планировщик из 930 и ветвь записи состояния. ### 9. Счётчик памяти включает полностью исключённые сообщения

В отдельном диалоге созданы два успешных хода. Через публичный API исключены обе стороны каждого хода. Состояние памяти того же диалога вернуло `remembered_turns=2`. Штатная выборка истории для модели на той же базе вернула пустой список. Причина — разный SQL для счётчика и для чтения. Установленный факт касается счётчика, утечки исключённых сообщений в этом опыте нет. В совместимом интерфейсе этот показатель подписан как число сообщений с ответами в памяти. ## Как должно выполняться одно обращение к документам

Этот порядок опирается на два локальных сравнительных опыта.

**Один адрес страницы, два разных факта.** Даны два фрагмента одной страницы 4. Первый сообщает базовую ставку 10, второй — исключение 12. В LlamaIndex Core 0.14.22 через публичный `CitationQueryEngine.query` с фиксированной выдачей и управляемой моделью оба фрагмента дошли во вход, получили разные номера, а ссылка [2] соответствовала тексту об исключении. На тех же фрагментах штатная функция разбора цитат из исходника ЛЕС 930 тоже правильно вернула только индекс 2 для ответа с [2]. При замене в ответе только ссылки на общий URL страницы ЛЕС вернул индексы 1 и 2. Значит, нумерация фрагментов в ЛЕСе уже решает эту задачу. Исправление нужно в том месте, где ссылка на страницу засчитывается за цитирование всех её фрагментов. В опыте LlamaIndex проверена нумерованная ссылка, поддержка им произвольной Markdown-ссылки не оценивалась. [Проверка текста источника в LlamaIndex](https://developers.llamaindex.ai/python/examples/query_engine/citation_query_engine/) · [Разбор URL в ЛЕСе](../../core/src/citations.rs#L202)

**Файл вне первых результатов, но внутри выбранной папки.** В локальный Qdrant Client 1.18.0 в памяти помещены четыре записи с контролируемыми векторами — A, B, `current/Notes.txt`, `archive/Notes.txt`. Поиск по вектору с пределом 2 вернул A и B. На тех же данных точное чтение по набору и полному относительному пути вернуло только ID 3 для `current/Notes.txt`. Функция распознавания ЛЕСа при выдаче из одних A и B получила только A и B даже при наличии точного пути в вопросе, как показано в находке 2. Это сравнение двух способов разрешить явно названный файл. Оно показывает, какую гарантию даёт отдельный поиск по ключу. ## Критерии выпуска и оценка качества

Основной рабочий сценарий пользователя — вопрос по датасету или папке. Для его проверки задают только область и обычный вопрос. Имена файлов, ID обязательных документов и адреса страниц остаются в эталоне для оценки. Сценарий с ручным выбором файлов проверяет отдельную возможность.

**Контроль на 931.** В изолированной локальной библиотеке для каждого прогона создан один набор с короткими TXT и числовыми именами. Три разных документа задают давление на севере (184 кПа), давление на юге (273 кПа) и общее условие (охладить теплоноситель до 26 °C). Сначала в наборе было 12 файлов. Во втором прогоне добавлены 48 похожих записей о приёмке другого оборудования. Вопрос содержал только названия участков и спрашивал давления и условие начала испытаний. Нативный API индексировал папку через Qdrant и локальную BGE-M3. В обоих прогонах при управляемом ответе все три факта присутствовали в первом сообщении провайдеру. При 60 документах отдельный поисковый запрос вернул 11 источников, нужные заняли позиции 1, 2 и 5. В первом сообщении чата с тестовым профилем были представлены источники из всех 60 файлов. Это один положительный вопрос в двух размерах корпуса. Он проверяет доставку, но оставляет открытым выбор объёма контекста на реальных папках.

**Живой ответ по папке из 60 файлов.** В отдельном прогоне с BGE-M3 и локальной Qwen3.5 2B через совместимый API (запрошенное окно 8192) оба вопроса завершились HTTP 503 с кодом `UPSTREAM_RESPONSE_TOO_LARGE`. Первый вопрос — о двух давлениях и температуре. Второй — о сроке гарантии, который в корпусе не указан. В обоих случаях пользователь остался без ответа. В отрицательном примере техническая ошибка не засчитывается как обоснованный отказ. Код встречается в нескольких проверках транспорта, поэтому конкретный превышенный предел этим прогоном не установлен. Для следующего изменения нужен повтор с записью числа и размера событий потока и фактического объёма запроса в профиле живой модели.

1. **Неизменяемые свойства программы.** Во всех подготовленных обязательных примерах чужой ID документа, повторная запись одного хода и переход к чужому оригиналу считаются ошибкой. Ложная готовность и восстановление без рабочего каталога также блокируют соответствующий выпуск. При нехватке окна или недоступном источнике ожидается явный частичный результат или объяснённый отказ. Здесь возможна точная проверка ожидаемого исхода в каждом случае.
2. **Поиск и доставка.** Для положительного вопроса фиксировать число требуемых файлов и их попадание в первые 10 и 64 позиции, затем в прочитанные фрагменты и в фактическое сообщение модели. Отдельно считать долю нужных фактов и оговорок, дошедших в первый и в последний вызов. Для сравнения двух кандидатов использовать те же документы и вопросы. Публиковать числитель, знаменатель и список ухудшившихся случаев по типам документов. Старые корпусные числа не служат порогом для другой сборки.
3. **Качество ответа живой модели.** В каждой размеченной задаче отдельно оценивать правильность факта, сохранение условия, подтверждение цитатой и точность места в оригинале. В отрицательных примерах считать неподтверждённые утверждения и обоснованные отказы. Указывать модель, её редакцию, параметры и число повторов. Для первого сравнения предлагаю три повтора каждого критического сценария и ручную проверку спорных утверждений по оригиналу. Внешнюю модель сравнивать на синтетическом или специально разрешённом корпусе. Целевой процент для всего корпуса назначать после первого замера и просмотра ошибок по классам.
4. **Сквозной выпуск.** Чистая Windows, полный установщик, новый проект, назначение моделей, индексация папки, вопрос по нескольким файлам, обрыв/возврат, клик по цитате, обновление и откат. Для каждого прогона записать версии приложения, индекса и моделей, результат пользователя, время до первого текста и до проверяемой ссылки. Падение проверки ресурсов учитывать отдельным исходом до вызова провайдера. На этой основе можно принять или вернуть кандидата по конкретному свойству.

## Границы проверки

Использованы исполняемый API кандидата 930, временные базы SQLite, синтетические файлы, управляемый ответ хранилища, отдельно скомпилированные функции Rust из проверяемого коммита и настоящий код интерфейса. Контрольные суммы бинарного файла API и исходников совпали с паспортом кандидата. В первом проходе прошли 17 интерфейсных тестов, включая две проверки этого разбора. ## Предлагаемая граница между чатом и библиотекой

**Результат первого этапа, 931.** Явно выбранные оригиналы разрешаются по каталогу до поиска. Проверены запрос по трём PDF без индекса, оба способа запроса трёх TXT, отсутствующий оригинал при наличии архива, тесное окно, сохранение выбора и клик на источник. На тех же трёх PDF локальная Qwen вернула обе величины и оговорку. При русском вопросе одна фраза в ответе была искажена, хотя источники и итоговые величины были верны. Следующая граница проверки — свободный тематический поиск на размеченном корпусе и повторяемость показателей на нескольких вопросах. [Результаты 931](../RELEASE_LEDGER.md) · [Реализация](../../api/src/chat/tools/sources/selection.rs)

**Решение.** Передать библиотеке документов ответственность за выбор оригинала, его редакцию, чтение и координаты фрагментов. Оставить чату смысл вопроса, запрос дополнительных материалов и формулировку ответа. Оба компонента помещаются в текущем процессе Rust. Один и тот же запрос к библиотеке можно выполнить из чата, MCP или диагностики при одинаковой области доступа. Граница уже частично есть в публичном API инструментов. Сейчас при предварительном поиске чат сам выводит список названных документов из выданных кандидатов. Если нужный файл выпал раньше, чат может считать задание выполненным по оставшимся. [Вход инструментов](../../api/src/chat/sources_api.rs#L129) · [Порядок в чате](../../api/src/chat/runner.rs#L118) · [Сопоставление имён](../../api/src/chat/inspection.rs#L75)

| Действие пользователя | Как его исполнять |
| --- | --- |
| Выбрал папку, спросил «какие условия приёмки?» | Папка задаёт разрешённую область. Hybrid находит кандидатов, читатель извлекает фрагменты, модель при необходимости запрашивает ещё. |
| Выбрал два файла для сравнения или явно попросил открыть точный путь | До поиска зафиксировать ID каждого обязательного файла в области. Поиск внутри большого оригинала может выбрать страницу или строки. Для каждого обязательного файла сохранить, какой материал дошёл и что осталось недоступно. |
| Спросил «где упоминается Notes.pdf?» | Искать упоминание. Имя в тексте вопроса само по себе не обязывает читать файл. Если пользователь попросил открыть файл только по имени и в области два совпадения, показать оба пути для выбора. |
| Общается без обращения к библиотеке | Обычный ход чата. Чтение, проверка ссылок и табличные инструкции включаются только в подходящем режиме. |

**Что передаётся между компонентами.** В задании фиксируются разрешённая область, обязательные документы и цель чтения. Результат библиотеки содержит ID документа, редакцию, координату, текст и сведения о неполном чтении. Сборщик контекста отмечает, какие фрагменты вошли в конкретное сообщение провайдеру. По этой записи сервер проверяет ссылку, а интерфейс открывает оригинал. Соответствие ссылки отправленному фрагменту можно проверить программно. Подтверждает ли фрагмент вывод модели, оценивается отдельно. В специальном режиме разбора документов уже есть привязка цитаты к версии прочитанного диапазона. Её можно использовать отдельно от дорогого режима сплошного просмотра. [Проверка диапазона цитаты](../../core/src/document_review/quotes.rs#L17) · [Сборка окна](../../core/src/chat_context/assembly.rs#L28) · [Жизненный цикл разбора документа](../modules/native-document-review.md#L24)

**Что работает сегодня.** В отдельном временном экземпляре API 930 зарегистрированы два синтетических одностраничных PDF с одинаковым коротким именем. Через `POST /api/rag/sources/call` каталог вернул `archive/Notes.pdf` и `current/Notes.pdf`. Чтение по набору и пути `current/Notes.pdf` вернуло страницу 1 с условием «12 после проверки» и SHA-256 текущего оригинала. Запрос отсутствующего пути вернул HTTP 404 с `SOURCE_DOCUMENT_NOT_FOUND`. Замена содержимого оригинала на том же пути вернула HTTP 409 с `PDF_REVISION_CHANGED`. Во всех случаях было ноль вызовов модели. Каталог для этого опыта подготовлен тестовой оснасткой. В отдельном опыте с добавлением двух текстовых файлов индексатор сообщил `INDEX_MEMORY_GUARD`. Сквозное сравнение путей чата на свежем индексе остаётся первым испытанием кандидата. [Точный выбор каталога](../../core/src/catalog/library.rs#L190) · [Чтение PDF](../../api/src/chat/tools/sources.rs#L198) · [Оснастка оригиналов](../../tests/test_light_native_chat_turn.py#L145)

**Как перейти и когда удалить старый код.**

1. Сохранить сообщения, реально полученные провайдером на 930, для сравнения трёх документов с оговоркой, одноимённого архива, обязательного документа вне выдачи и свободного вопроса по папке. Включить случаи отсутствия файла, смены редакции, тесного окна и обычного чата. Зафиксировать число обращений к модели и время до ответа.
2. В локальном кандидате перевести только явное чтение и сравнение на новый порядок. Использовать существующие каталог, читатели и упаковщик. Тест отправляет обычный запрос чата. Проверяются набор ID, текст с оговоркой в запросе провайдеру, версия и координата клика в ответе либо видимое пользователю объяснение неполноты. Повторить с живой локальной моделью для оценки выводов.
3. После прохождения этих проверок подключить тематический поиск к тому же чтению и учёту фрагментов. Сравнить обе реализации на одном индексе и корпусе по попаданию фактов во вход, качеству ответа, задержке и числу вызовов. При падении полноты или росте задержки локализовать потери до переключения. Для свободного поиска отдельно оценивать выбор кандидатов.
4. После переключения удалить вывод обязательных ID из поисковых кандидатов, общую табличную инструкцию и ветви повторного ответа, которые только компенсировали потерю источника. Оставшиеся повторы привязать к конкретной причине с пределом попыток. Проверить прежние входы JSON, SSE и MCP. Индекс, формат пользовательской библиотеки и установщик для первого этапа мигрировать не требуется.

**Проверка с удалённым эталоном.** В предоставленном отчёте RAGHOUND точный код дал 30/30 попаданий нужной карточки в первую шестёрку при 16/30 у обычного Hybrid. Полный зачёт с точным кодом получили по 26/30 обе модели. В отдельной серии без эталонного ID Qwen правильно воздержался в 8/8, Liquid — в 0/8. В сценарии обязательного оригинала это основание проверить собственный отказ программы до генерации. В тесте ЛЕСа текущая редакция исчезает из каталога, одноимённая архивная остаётся, счётчик обращений к провайдеру должен остаться прежним. В свободном тематическом поиске отсутствие подходящего фрагмента требует отдельной оценки поведения модели. Цифры RAGHOUND относятся к внешнему стенду автора отчёта.
