# Qdrant Edge: проверка встроенного BM25

Статус 17–18 ноября 2026: возможности сверены с официальной документацией и
исходниками уже установленного Rust-пакета `qdrant-edge = 0.9.0`.
**Поиск и 400 MCP-вызовов на копии проверены. Рабочее переключение не принято:**
прежние токены сохраняют качество, нативный анализатор ухудшает доставку;
ускорение ядра не подтверждает ускорение всего пути. Ниже протокол и результаты.

В кандидате 893 подготовлен отключённый по умолчанию адаптер опыта.
Для `matched-v1`/`raw-v1`/`context-v1` нужны `LES_EXPERIMENT_EDGE_BM25` и маркер
`les.edge-bm25-trial.v1` в корне копии с точными root/collection/revision.
Подготовка отмечается preparing → ready, проверяет исходные payload/векторы
до и после добавления двух производных полей. Без готового маркера
или при незавершённой/изменившейся публикации запрос завершается отказом.
Это защита стенда, не приёмка рабочего переключения. Код собирается на GitHub;
частные документы и индекс туда не отправляются.

При подготовке копии обнаружена ошибка самого испытательного контроля:
порядок полей JSON из SDK нестабилен при равных значениях. Четыре чтения
88 175 точек дали разные прежние хеши; повторные 64 точки имели равные
значения и одинаковую сортированную сериализацию в двух сборках. До поиска
контроль остановил опыт; такие прогоны не входят в метрики качества.
Исправленный алгоритм `les.edge-points.sorted-json.v1` рекурсивно сортирует
объекты, сохраняя числа и порядок массивов. Неверсионированный старый хеш
отклоняется; автоматического пересоздания эталона нет. Старый протокол
сохраняется отдельно, новый снимок явно фиксируется до подготовки.
Регрессия использует несколько named vectors, вложенные payload, повторные
чтения и переоткрытие индекса. Корпусная сверка описана отдельно ниже.

Для ограниченной RAM предусмотрен отдельный явный `LES_EXPERIMENT_QUERY_CACHE`:
векторы прежних 100 запросов BGE, без ответов/эталонов. Модель, её manifest hash,
recipe и когорту сверяет испытательный драйвер; Rust дополнительно проверяет
привязку локальной роли, корня копии, снимка точек, размерность и норму.
Незнакомый запрос — ошибка, не скрытый вызов другой модели. Этот офлайн-опыт
не проверяет доступность живого embedding-сервера и не продлевает его capability
snapshot. В обычном запуске кэш выключен и действует прежняя проверка модели.
Все плечи получают те же query-векторы; замеры не выдаются за задержку живого BGE.

## Что подтверждено

- [BM25 в Edge](https://qdrant.tech/documentation/edge/edge-bm25/): полнотекстовый
  индекс payload с включённым scoring и `TextQuery`; sparse BM25 — отдельный путь.
- [Чтение Edge](https://qdrant.tech/documentation/edge/edge-api/reading-data/):
  текстовый запрос можно использовать в prefetch для гибридного поиска.
- В локальных исходниках 0.9.0 `VectorStorageDatatype` содержит Float32,
  Float16, Uint8, Turbo4, Turbo8, Turbo16. Это подтверждает наличие API, а не
  качество сжатого поиска на корпусе LES.
- `TokenizerType::Code`, поля `TextIndexParams.scoring` и `.nested` также
  присутствуют в локальном SDK. Их применение к данным LES ещё не проверено.
- Встроенный полнотекстовый индекс строится по существующему payload.
  Пересчитывать dense-векторы для этого не нужно; сам индекс текста всё равно
  требуется построить, а затраты измерить.

## Текущее устройство LES

`vector/Cargo.toml` уже закрепляет Edge 0.9.0. Обновлять его до номера версии
Server не требуется. Основной BM25 — собственные postings SQLite
(`vector/src/postings.rs` → `core/src/bm25.rs`), **не SQLite FTS**.
Упоминание Tantivy в исследовательских зависимостях не означает, что основной
поиск сейчас работает через Tantivy.

`lexical::current` сейчас вызывает `versioned(..., LEGACY)`, то есть
`les.lexical.v2`. Наличие отдельного Snowball-анализатора v3 не доказывает,
что он включён в основном пути. Новый Edge Snowball нельзя считать тем же
самым анализатором без проверки.

`vector/src/operations.rs::scoring` поддерживает dense/sparse/multidense и fusion,
до 892 **не переводил TextQuery** в нативный запрос Edge. В 893 добавлен
перевод с фиксированными k=1.2/b=0.75; корпусная проверка приведена ниже.

## Один опыт — одно изменение

| Плечо | Лексическая ветвь | Dense и слияние |
|---|---|---|
| A, контроль | Нынешний SQLite BM25 с зафиксированной версией анализатора | Неизменные BGE и текущий RRF LES |
| B0, контроль движка | Edge BM25 на тех же подготовленных токенах, без второго стемминга | Те же BGE, ранги dense, RRF и фильтры LES |
| B1, полный кандидат | Edge BM25 по существующему тексту с нативным анализатором | Те же BGE, ранги dense, RRF и фильтры LES |
| B2, контроль представления | Edge BM25 по полному `search_context::input`, включая прежние заголовки | Те же BGE, ранги dense, RRF и фильтры LES |
| C, следующий отдельный опыт | Принятый вариант B1 | Нативный hybrid Query API при явно тех же параметрах |

B0 использует только на копии производное поле с прежними токенами и их TF,
Whitespace-tokenizer без stopwords/стемминга; строки/поля оригинального текста,
структуры и dense-векторы неизменны. Его область статистики и обработку пустых
текстов нужно сверить с контролем. Это диагностический способ отделить смену
движка от изменения анализа, не предложение оставить второй текстовый формат
в приложении. B1 проверяет конечное упрощение без этого производного поля.

B2 зарегистрирован до получения корпусных поисковых результатов. Нынешняя
индексация использует `search_context::input`, а не только payload.text;
отказ от prefix вместе со сменой движка терял бы часть заголовков.
`context-v1` сохраняет тот же вход и меняет только нативный анализатор/движок.
Это не дополнение текста по эталону или формулировке вопроса. Его временное
поле, как и поле токенов B0, исключается из проверки неизменности оригинальных
payload, но все остальные поля и векторы обязаны остаться побитно теми же.

Не включать одновременно Turbo, другой токенизатор для кода, новые чанки,
реранкер, изменение RRF или отбор контекста. Не использовать неявные значения
SDK вместо фактических параметров профиля LES. Не объявлять разные методы
равноценными по отсутствию статистически значимой разницы.

Для B1 фиксируются: tokenizer, lowercase, границы токенов, min/max token length,
Snowball Russian, stopwords, k/b и область статистики корпуса. Поиск внутри
одного набора проверяется отдельно от поиска по обоим: фильтрация результатов
не означает автоматически пересчёт BM25-статистики по выбранному набору.
Различия разбора русских слов, смешанной кириллицы/латиницы, составных кодов,
дефисов и десятичных чисел входят в результаты, а не скрываются нормализацией
под конкретный вопрос. Одинаковую нормализацию индекса и запроса проверять явно.

## Протокол корпуса и метрики

Использовать одну существующую частную копию, без новых полных копий индекса.
Перед изменением payload-индекса: проверить владельца, остановку API копии,
idle-поколение и отсутствие незаконченной публикации; зафиксировать конфигурацию,
точки, payload и векторы. Рабочая установка/индекс не открываются для записи.

Старая диагностическая сотня вопросов: SHA-256
`a57ea79f2049413d93cf0589200e02d67c7783c1b30c6d34bc9a68bb866b1677`.
Её повторное использование не является независимой приёмкой. Ожидаемые имена
файлов, ID и страницы не передаются в поиск, эталон применяется после выдачи.

Сначала проверить идентичность BGE query recipe, модели и размерности сохранённых
запросных векторов с текущим индексом. Старый кэш другого провайдера/формата нельзя
считать совместимым только по имени bge-m3 и размерности 1024.

Измерять отдельно:

1. BM25 без dense: покрытие нужных источников в top-5/10, обозначения и числа.
2. Dense + BM25 с тем же RRF: top-5/10/64, состав и ранги каждой ветви.
3. После выбора кандидата — реальный `search_sources` через MCP с тем же бюджетом:
   доставленные источники, точные цитаты/страницы/строки, ошибки дочитывания.
4. Построение текстового индекса, холодный/тёплый запуск, p50/p95, RAM и размер;
   отдельно от генератора, без Qwen и без загрузки новой модели.
5. Обновление/удаление/восстановление на копии: никакой смеси редакций;
   штатный журнал публикации LES не заменяется отдельной успешной операцией Edge.

При наличии только файлового эталона результат называется долей нужных
источников в top-k, не Recall@k по всем релевантным чанкам. Для полноценного
chunk-recall нужна соответствующая разметка. Отрицательные и визуальные
диагностические случаи оцениваются отдельно, без выдуманной точности ответа.

Публикуются все парные изменения, интервалы и знаменатели, включая ухудшения.
Потери при поздней упаковке измеряются отдельно: новый BM25 сам по себе не
устраняет ошибки передачи уже найденного доказательства в контекст.

## Решение о замене

Если выбранное плечо сохраняет качество, фильтры, точные обозначения и восстановление, можно
рассматривать удаление **лексических postings** из SQLite. Сам SQLite остаётся
владельцем каталога, состояния и памяти; удалять его целиком оснований нет.
Недостаточно одного общего среднего при регрессии чисел, редакций или цитат.

Turbo и nested проверяются позже отдельными опытами. Обновление зависимостей
или рабочего LES этим документом не выполняется.


## Результаты поискового этапа, 17–18 ноября 2026

Копия: 638 документов, 88 175 точек. Контроль и три варианта Edge получили
одинаковые 100 запросов и сохранённые BGE-векторы. Качество источников оценено
на 90 положительных случаях; три вопроса без ответа и семь визуальных
диагностических случаев сохранены отдельно. Это повтор разработки, не новый
независимый тест. Рабочий Лес 880 не менялся.

Код опыта: `3630c6369cb90597b124f3971e6b9aec605b2ea6`.
[Облачная сборка и нативные проверки](https://github.com/proovcme/LES/actions/runs/44159160098).
Контроль **уже использует dense в Edge**; ниже сравниваются SQLite postings
и текстовый BM25 Edge, а не Server и Edge.

### Контроль корректности и границы опыта

- Сняты все 1200 лексических запросов (100 × 4 × 3 области) и 400 гибридных.
  Выходов за выбранные наборы нет. Поиск не получал ожидаемый файл, ID или страницу.
- Проверены TF, длины, dataset/file/role, DF и корпусная статистика всех 88 175
  SQLite-записей: 7 138 855 вхождений, 140 902 термина; расхождений нет.
- На каждом вопросе dense-ветвь до и после четырёх вариантов совпала: 100/100.
- В B0/B2 полнотекстовый индекс содержит 88 175 точек; в B1 — 87 935:
  240 исходных текстов не дали Word-токенов. Это различие представления, не
  исчезновение документов или векторов.
- Нативная подготовка двух полей и трёх текстовых индексов заняла 458,25 с.
  Это диагностический стенд с тремя индексами одновременно, не замер стоимости
  одного производственного варианта. Dense-векторы не пересчитывались.
- Оптимизация изменила ранги прежнего гибридного контроля в 69/100 вопросах
  при неизменных исходных значениях. Две сборки на состоянии после оптимизации
  дали одинаковую повторную выдачу проверенного запроса. Поэтому все четыре
  варианта выше сравнивались **на одном состоянии после подготовки**; изменение
  относительно старого состояния не выдаётся за эффект нового BM25.
- Финальная сплошная сверка остановлена наблюдателем при RAM ниже 4 ГиБ уже
  после всех поисковых запросов. Исходный остановленный журнал сохранён.
  Отдельная точная сверка 11 короткими процессами по ≤8192 точки сохранила
  исходные числовые JSON-лексемы и получила тот же нативный SHA-256 всех
  payload/векторов. Совпал также исходный отпечаток каталога 638 документов.
  Порог RAM не ослаблялся, повторные вопросы не подменялись.

выключенный реранкер и читатель `original-v1` / `section-v1`. Варианты
распределены четырьмя периодами; API перезапускается после максимум четырёх
вопросов для каждого варианта. Время всей серии — 4558,18 с.

Доля источников — среднее покрытия ожидаемых файлов по вопросам; покрытие
текста — среднее покрытия 5-грамм эталонных цитат из нужного источника.
«Нужная страница найдена» требует хотя бы одну ожидаемую страницу; это не
полное покрытие многостраничного ответа. Средняя доля ожидаемых страниц:
87,50% у A/B0 и 79,17% у B1/B2. Две проверяемые строки XLSX доставлены 2/2
во всех вариантах. Показатели не измеряют правильность ответа генератора.

B0 сохранил каждую из измеренных метрик качества по каждому вопросу, а не
только общее среднее. У B1/B2 изменение доставки −2,78 п.п., парный 95% CI
−8,33…+2,78 п.п. Изменение покрытия текста B1: −1,45 п.п., CI −8,70…+5,80;
B2: −2,90 п.п., CI −10,14…+4,35. Нативный анализатор не принят как улучшение.

Четыре обзорных вопроса: доставка A/B0 — 29,17%, B1/B2 — 16,67%; медиана
MCP — 12,13 / 14,12 / 37,64 / 27,09 с. Это малая диагностическая подгруппа.

Найденная общая потеря после поиска: в 90 положительных вопросах 101 ожидаемая
пара «вопрос — файл». У A/B0 91 присутствует в отдельной гибридной выдаче @64,
70 доставлены MCP; 21 найдена, но отсутствует в пакете. У B1/B2 — 90 и 67,
соответственно 23. Это количества пар, не уникальных документов и не среднее
по вопросам из таблицы. Отдельные вызовы поиска и MCP показывают потерю между
пулом и пакетом, но не доказывают конкретную внутреннюю операцию отбрасывания.
Замена BM25 сама эту проблему не решает.

### Числа и независимая проверка оригиналов

В 21 числовом случае доля присутствующих ожидаемых чисел: A/B0 — 80,95%,
B1 — 78,57%, B2 — 80,95%. Все ожидаемые числа найдены в 16/21 случаях у
каждого варианта. В 13 случаях с заданной страницей/строкой соответствующий
показатель с проверкой местоположения: A/B0 — 88,46%, B1/B2 — 80,77%.
Это диагностика наличия, **не точность связи числа с колонкой и не точность
числового ответа**. Замороженный скалярный анализатор также не разбирает
составные размеры как полноценную пару величин; эталон после опыта не менялся.

Дополнительно визуально просмотрены четыре реально процитированные страницы
трёх PDF, а две строки XLSX сверены непосредственно с OOXML и шапкой таблицы.
Проверка опиралась на выданные MCP идентификаторы и SHA, не направляла поиск
на заранее выбранный файл. Обнаруженные границы результата:

- В двух строках XLSX сохранены позиция, марка, единица и количество; значения
  совпали с исходными ячейками. В этих двух строках формул нет: это не проверка
  пересчёта формул и не приёмка всех таблиц.
- В просмотренных PDF значения строк совпадают с изображением, но обычный
  текстовый фрагмент иногда отделяет единицы от строк или теряет шапку.
  Наличие верной ссылки на страницу не исправляет такое представление таблицы.
- В вопросе по двум страницам доставлена первая, второй нужной страницы нет;
  в отдельном вопросе тот же источник с третьей страницей доступен. Для одного
  вопроса по позиции нужного файла нет вовсе. При B1/B2 ещё один числовой вопрос
  получает первую страницу вместо нужной третьей. Эти потери не скрыты общей
  средней метрикой и не исправлены под конкретную формулировку.

Независимые проверки всех 104 серий: 2144 повторных проверки байтов файлов,
1699 чтений PDF-страниц и 826 проверок Word-единиц, ошибок 0. Уникально проверены
238 пар «документ — SHA» и 517 PDF-страниц. Для PDF проверялись исходный SHA,
идентификатор, страница и дочитывание до конца с непрерывным курсором. Для Word
проверялись исходные позиции и текст. В доставленных пакетах нет единиц с тегом
`physical_pdf_unit`: утверждать точное побайтовое соответствие **каждого тела
индексного PDF-фрагмента** независимому физическому чтению этот проверяющий
скрипт не позволяет. Визуальная проверка четырёх страниц — отдельная проверка.

### Скорость полного пути и память

Ускорение поискового ядра **не перешло в ускорение MCP**. Парная медиана
добавочной задержки B0 — +3,82 с, 95% CI +2,74…+5,45 с. Логи всех 400 вызовов
связывают замедление с чтением PDF/Word, а не с поиском:

| Медианная фаза, мс; все 100 вопросов | A | B0 | B1 | B2 |
|---|---:|---:|---:|---:|
| Поисковое хранилище | 194,5 | 96 | 92 | 87,5 |
| Word | 610 | 1075 | 1068 | 1059,5 |
| PDF | 1561,5 | 4613 | 5378,5 | 5234 |
| Упаковка | 116,5 | 118 | 119 | 111 |

Медианы отдельных фаз нельзя складывать как медиану общего времени.
У B0 число запланированных областей совпадает с A в 99/100 вопросах,
список point ID квитанции — в 95/100. Одним ростом объёма найденных документов
такую задержку объяснить нельзя. Эти измерения локализуют фазу; причинную
связь с движком, состоянием файлового кеша или конкурирующим I/O ещё нужно
разделить. Сводка не объявляет ускорение всего RAG.

Дополнительный повтор ABBA/BAAB: восемь свежих API, один и тот же вопрос,
выбранный по близости к медианной парной разнице среди случаев с одинаковыми
областями и квитанциями; без выбора по эталону. Все восемь квитанций совпали.
Первый A занял 25,16 с, остальные A — 8,89–8,98 с, B0 — 8,08–8,74 с.
Разница читателей из полной серии здесь устойчиво не воспроизвелась; холодное
чтение существенно влияет на результат. Этот малый повтор не заменяет 400
вызовов и не доказывает конкретную причину. Нужен отдельный опыт с измерением
попаданий кеша и I/O перед утверждением о замедлении именно из-за BM25 Edge.

В завершённой серии минимум доступной RAM — 4,88 ГиБ, пик собственных процессов
— 2,32 ГиБ, минимум свободного диска — 22,83 ГиБ. Локальный Rust-компилятор
не запускался; сборка выполнена на GitHub. Живые BGE-запросы заменены явно
проверенными сохранёнными векторами; Qwen и другие генераторы не вызывались.
Доставка здесь означает пакет `search_sources`, не фактический промпт модели.

Предыдущая длинная серия A остановлена внешним наблюдателем по RAM на 18-м
вызове. Тот же вопрос в свежем API прошёл с проверкой цитат, холодное чтение
заняло 90,42 с. Поэтому полный парный повтор проведён равными сериями максимум
по четыре вопроса. Это политика стенда, **не исправление памяти долгоживущего
приложения**. Остановленные журналы сохранены и не включены в итоговую серию.

Закрытая диагностическая копия занимает 1,60 ГиБ и содержит сразу три текстовых
индекса. Чистого замера дискового прироста одного кандидата здесь нет: снимок
размера до завершения подготовки уже содержал часть производных полей.
Временные PDF-копии и изображения визуальной проверки удалены после просмотра;
их SHA и выводы сохранены в частном журнале. Рабочие данные и исходники не удалялись.

### Целостность, воспроизводимость и решение

После всех 400 MCP-вызовов повторно сверены все 88 175 исходных payload и
векторов: тот же SHA-256
`94dd7056104fbaa5cc059b78c07f8de331033f19ed12c51478376c6eca439599`
по `les.edge-points.sorted-json.v1` (исключены только два производных поля и
служебная версия). Совпали каталог, idle-журнал и SHA всех 638 оригиналов.
Сверка ограниченными SDK-процессами заняла 166,25 с. Новых полных копий индекса
и перерасчёта dense-векторов не делалось.

[Полный CI того же исходного кода](https://github.com/proovcme/LES/actions/runs/44159160064):
core 177, runtime 8, API Edge 149, mail 66; frontend 57 тестов. `make test`:
2217 passed, 23 skipped, 18 subtests. `make verify`: 2240 collected — это
сбор контрактов, не ещё 2240 выполненных поведенческих теста. Эти проверки не
подменяют описанный корпусный опыт. Рабочий UI в этом задании не менялся.

В частном журнале сохранены исходная когорта и векторы с хешами, привязка BGE,
облачные receipt и SHA исполняемых файлов, подготовка, все 1600 поисковых
результатов, 400 MCP-пакетов, независимые чтения, парные метрики и интервалы,
пофазные логи, разбор потерь и финальный отпечаток. Пользовательские вопросы,
выдержки, пути и оригиналы в GitHub не отправляются.

**Решение: рабочий Лес не переключать.** B0 сохраняет измеренное качество и
ускоряет лексическое ядро, поэтому остаётся кандидатом замены postings.
Следующие условия приёмки: воспроизводимая задержка полного пути, устранение
потерь найденных страниц/табличных единиц и проверка обновления/падения реальной
партии с новым текстовым индексом. Нативный анализатор B1/B2 не принимается.
Синтетическая проверка журнала не выдаётся за такую корпусную аварийную приёмку.
