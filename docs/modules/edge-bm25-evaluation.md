# Qdrant Edge: проверка встроенного BM25

Статус 17 ноября 2026: возможности сверены с официальной документацией и
исходниками уже установленного Rust-пакета `qdrant-edge = 0.9.0`.
**Корпусный сравнительный прогон ещё не выполнен.** Это протокол опыта,
не переключение штатного поиска, моделей или решение о миграции.

В кандидате 893 подготовлен отключённый по умолчанию адаптер опыта.
Для `matched-v1`/`raw-v1`/`context-v1` нужны `LES_EXPERIMENT_EDGE_BM25` и маркер
`les.edge-bm25-trial.v1` в корне копии с точными root/collection/revision.
Подготовка отмечается preparing → ready, проверяет исходные payload/векторы
до и после добавления двух производных полей. Без готового маркера
или при незавершённой/изменившейся публикации запрос завершается отказом.
Это защита стенда, не приёмка рабочего переключения. Код собирается на GitHub;
частные документы и индекс туда не отправляются.

При подготовке копии обнаружена ошибка самого испытательного контроля:
порядок полей JSON из SDK нестабилен при равных значениях. Четыре чтения
88 175 точек дали разные прежние хеши; повторные 64 точки имели равные
значения и одинаковую сортированную сериализацию в двух сборках. До поиска
контроль остановил опыт; такие прогоны не входят в метрики качества.
Исправленный алгоритм `les.edge-points.sorted-json.v1` рекурсивно сортирует
объекты, сохраняя числа и порядок массивов. Неверсионированный старый хеш
отклоняется; автоматического пересоздания эталона нет. Старый протокол
сохраняется отдельно, новый снимок явно фиксируется до подготовки.
Регрессия использует несколько named vectors, вложенные payload, повторные
чтения и переоткрытие индекса. Это ещё не результат корпусной приёмки.

Для ограниченной RAM предусмотрен отдельный явный `LES_EXPERIMENT_QUERY_CACHE`:
векторы прежних 100 запросов BGE, без ответов/эталонов. Модель, её manifest hash,
recipe и когорту сверяет испытательный драйвер; Rust дополнительно проверяет
привязку локальной роли, корня копии, снимка точек, размерность и норму.
Незнакомый запрос — ошибка, не скрытый вызов другой модели. Этот офлайн-опыт
не проверяет доступность живого embedding-сервера и не продлевает его capability
snapshot. В обычном запуске кэш выключен и действует прежняя проверка модели.
Все плечи получают те же query-векторы; замеры не выдаются за задержку живого BGE.

## Что подтверждено

- [BM25 в Edge](https://qdrant.tech/documentation/edge/edge-bm25/): полнотекстовый
  индекс payload с включённым scoring и `TextQuery`; sparse BM25 — отдельный путь.
- [Чтение Edge](https://qdrant.tech/documentation/edge/edge-api/reading-data/):
  текстовый запрос можно использовать в prefetch для гибридного поиска.
- В локальных исходниках 0.9.0 `VectorStorageDatatype` содержит Float32,
  Float16, Uint8, Turbo4, Turbo8, Turbo16. Это подтверждает наличие API, а не
  качество сжатого поиска на корпусе LES.
- `TokenizerType::Code`, поля `TextIndexParams.scoring` и `.nested` также
  присутствуют в локальном SDK. Их применение к данным LES ещё не проверено.
- Встроенный полнотекстовый индекс строится по существующему payload.
  Пересчитывать dense-векторы для этого не нужно; сам индекс текста всё равно
  требуется построить, а затраты измерить.

## Текущее устройство LES

`vector/Cargo.toml` уже закрепляет Edge 0.9.0. Обновлять его до номера версии
Server не требуется. Основной BM25 — собственные postings SQLite
(`vector/src/postings.rs` → `core/src/bm25.rs`), **не SQLite FTS**.
Упоминание Tantivy в исследовательских зависимостях не означает, что основной
поиск сейчас работает через Tantivy.

`lexical::current` сейчас вызывает `versioned(..., LEGACY)`, то есть
`les.lexical.v2`. Наличие отдельного Snowball-анализатора v3 не доказывает,
что он включён в основном пути. Новый Edge Snowball нельзя считать тем же
самым анализатором без проверки.

`vector/src/operations.rs::scoring` поддерживает dense/sparse/multidense и fusion,
до 892 **не переводил TextQuery** в нативный запрос Edge. В 893 добавлен
перевод с фиксированными k=1.2/b=0.75 для сравнения, ещё требующий проверки.

## Один опыт — одно изменение

| Плечо | Лексическая ветвь | Dense и слияние |
|---|---|---|
| A, контроль | Нынешний SQLite BM25 с зафиксированной версией анализатора | Неизменные BGE и текущий RRF LES |
| B0, контроль движка | Edge BM25 на тех же подготовленных токенах, без второго стемминга | Те же BGE, ранги dense, RRF и фильтры LES |
| B1, полный кандидат | Edge BM25 по существующему тексту с нативным анализатором | Те же BGE, ранги dense, RRF и фильтры LES |
| B2, контроль представления | Edge BM25 по полному `search_context::input`, включая прежние заголовки | Те же BGE, ранги dense, RRF и фильтры LES |
| C, следующий отдельный опыт | Принятый вариант B1 | Нативный hybrid Query API при явно тех же параметрах |

B0 использует только на копии производное поле с прежними токенами и их TF,
Whitespace-tokenizer без stopwords/стемминга; строки/поля оригинального текста,
структуры и dense-векторы неизменны. Его область статистики и обработку пустых
текстов нужно сверить с контролем. Это диагностический способ отделить смену
движка от изменения анализа, не предложение оставить второй текстовый формат
в приложении. B1 проверяет конечное упрощение без этого производного поля.

B2 зарегистрирован до получения корпусных поисковых результатов. Нынешняя
индексация использует `search_context::input`, а не только payload.text;
отказ от prefix вместе со сменой движка терял бы часть заголовков.
`context-v1` сохраняет тот же вход и меняет только нативный анализатор/движок.
Это не дополнение текста по эталону или формулировке вопроса. Его временное
поле, как и поле токенов B0, исключается из проверки неизменности оригинальных
payload, но все остальные поля и векторы обязаны остаться побитно теми же.

Не включать одновременно Turbo, другой токенизатор для кода, новые чанки,
реранкер, изменение RRF или отбор контекста. Не использовать неявные значения
SDK вместо фактических параметров профиля LES. Не объявлять разные методы
равноценными по отсутствию статистически значимой разницы.

Для B1 фиксируются: tokenizer, lowercase, границы токенов, min/max token length,
Snowball Russian, stopwords, k/b и область статистики корпуса. Поиск внутри
одного набора проверяется отдельно от поиска по обоим: фильтрация результатов
не означает автоматически пересчёт BM25-статистики по выбранному набору.
Различия разбора русских слов, смешанной кириллицы/латиницы, составных кодов,
дефисов и десятичных чисел входят в результаты, а не скрываются нормализацией
под конкретный вопрос. Одинаковую нормализацию индекса и запроса проверять явно.

## Протокол корпуса и метрики

Использовать одну существующую частную копию, без новых полных копий индекса.
Перед изменением payload-индекса: проверить владельца, остановку API копии,
idle-поколение и отсутствие незаконченной публикации; зафиксировать конфигурацию,
точки, payload и векторы. Рабочая установка/индекс не открываются для записи.

Старая диагностическая сотня вопросов: SHA-256
`a57ea79f2049413d93cf0589200e02d67c7783c1b30c6d34bc9a68bb866b1677`.
Её повторное использование не является независимой приёмкой. Ожидаемые имена
файлов, ID и страницы не передаются в поиск, эталон применяется после выдачи.

Сначала проверить идентичность BGE query recipe, модели и размерности сохранённых
запросных векторов с текущим индексом. Старый кэш другого провайдера/формата нельзя
считать совместимым только по имени bge-m3 и размерности 1024.

Измерять отдельно:

1. BM25 без dense: покрытие нужных источников в top-5/10, обозначения и числа.
2. Dense + BM25 с тем же RRF: top-5/10/64, состав и ранги каждой ветви.
3. После выбора кандидата — реальный `search_sources` через MCP с тем же бюджетом:
   доставленные источники, точные цитаты/страницы/строки, ошибки дочитывания.
4. Построение текстового индекса, холодный/тёплый запуск, p50/p95, RAM и размер;
   отдельно от генератора, без Qwen и без загрузки новой модели.
5. Обновление/удаление/восстановление на копии: никакой смеси редакций;
   штатный журнал публикации LES не заменяется отдельной успешной операцией Edge.

При наличии только файлового эталона результат называется долей нужных
источников в top-k, не Recall@k по всем релевантным чанкам. Для полноценного
chunk-recall нужна соответствующая разметка. Отрицательные и визуальные
диагностические случаи оцениваются отдельно, без выдуманной точности ответа.

Публикуются все парные изменения, интервалы и знаменатели, включая ухудшения.
Потери при поздней упаковке измеряются отдельно: новый BM25 сам по себе не
устраняет ошибки передачи уже найденного доказательства в контекст.

## Решение о замене

Если B1 сохраняет качество, фильтры, точные обозначения и восстановление, можно
рассматривать удаление **лексических postings** из SQLite. Сам SQLite остаётся
владельцем каталога, состояния и памяти; удалять его целиком оснований нет.
Недостаточно одного общего среднего при регрессии чисел, редакций или цитат.

Turbo и nested проверяются позже отдельными опытами. Обновление зависимостей
или рабочего LES этим документом не выполняется.
