# Нативный владелец служб · кандидат 775

Кандидат 802 добавляет команды `les.cmd start`, `stop`, `restart`,
`status` и `logs`. `stop` передаёт запрос текущему владельцу окна и
ждёт подтверждения штатного завершения. Запрос содержит идентификатор
конкретного запуска, старый запрос не останавливает новый экземпляр.
Открытый редактор сначала сохраняет черновик. Закрытие окна Classic
также завершает службы. `logs` показывает последние события запуска и
остановки. `les.cmd tools` показывает инструменты, `les.cmd tool ИМЯ`
принимает JSON через stdin и вызывает тот же код, что и MCP.

Кандидат 792 добавляет в `les-runtime` режим `--cli`. В пакетах с Rust
runtime команда `les.cmd` вызывает этот режим. Доступны прежние команды
`status`, `datasets`, `projects`, `search`, `ask`, `mcp`. CLI проверяет
адрес, идентификатор экземпляра и актуальность статуса перед запросом и
после ответа. Поиск без явного набора охватывает пользовательские наборы.

Внешний MCP-клиент запускает `native/runtime/les-runtime.exe` с двумя
аргументами `--cli` и `mcp`. С 801 доступны наборы и документы, создание
набора, подключение разрешённой папки, ход импорта, проекты и привязки,
чтение и запись рабочих файлов и памяти с ревизиями, поиск и полноценный
диалог через `les_chat`. В новом пакете старые Python-точки входа
только перенаправляют настроенные подключения в Rust. Реализация CLI и
шлюза на Python осталась для старой сборки без Rust runtime. Подключение
внешних MCP-серверов из чата пока Python.

Операции записи объявляют соответствующие MCP-аннотации. Файловый доступ
Codex подчиняется тем же правилам памяти и рабочих файлов, что и агент Леса.
Импорт и подготовка вложения папки используют действующую проверку разрешённых
корней и читают исходники. `les_chat` использует назначенную модель и общий
harness. Результат возвращается целиком после завершения; это не поток токенов.
Статус импорта и статусы отдельных документов проверяются раздельно.

Собранный `les.cmd` проверен в отдельной папке без Python и с системным
PATH. Он получил статус, наборы и проекты через API отдельного экземпляра.
MCP-клиент прошёл инициализацию и вызов инструмента через Rust напрямую и
через старую точку входа. Тесты с локальным сервером проверяют создание и
продолжение чатов, ссылки, отсутствие служебных наборов и смену экземпляра.
Они используют тестовый ответ модели.

`runtime/` — отдельный Rust executable, который заменяет `tools/light_launcher.py`
в явно выбранном режиме `les-light.exe --native-launcher`. Откат без этого флага
остаётся прежним. Отсутствующий native binary даёт ошибку, скрытого возврата к
Python-запускателю нет. Это этап переноса, API и NiceGUI пока запускаются на Python.

Модули: `config` — аргументы/очищенная среда; `control` — владелец файловых lock,
сигналы и канал родителя; `services` — Qdrant/API/UI и их деревья; `probe` —
ограниченные loopback-проверки; `journal` — публикация состояния и журнал причин.
Используется общий `core::JobGuard`, а не новая копия Win32 job-обёртки.

Владение совместимо с прежними `launcher.lock` и `qdrant/runtime.lock`: Rust и
Python не могут одновременно открыть одно состояние. Второй запуск не меняет
статус владельца. Browser-повтор проверяет ограниченные локальные URL, instance_id
и живой API, затем открывает прежнее окно браузера. API/UI стартуют параллельно;
Qdrant подтверждает и доступ со своим новым ключом, и отказ без ключа.

Пути/порты/приватный ключ Qdrant формируются заново для собственного процесса;
чужие QDRANT__ и модельные настройки окружения не наследуются. API/UI получают
прежний allowlist и собственные пути состояния. Назначения моделей не меняются.
JSON-конфиг Qdrant хранится в состоянии и удаляется при штатной остановке.
Расширенный Windows-путь storage сохраняет поддержку длинных имён.

Проверка живости не зависит от ответа модели. Шесть последовательных неудачных
проверок службы запускают восстановление; падение PID замечается отдельно.
До трёх перезапусков за пять минут, затем error с причиной RECOVERY_LIMIT.
Перед новой парой API/UI предыдущие процессы и потомки завершаются. При нормальном
закрытии/EOF канала родителя владелец останавливается, причина записывается явно.
Windows Job закрывает потомков при аварийном завершении native owner. На Unix
применяются process groups; аварийный SIGKILL родителя остаётся отдельной приёмкой.

Статус совместим с Tauri: `launcher-status.json`, атомарная замена, PID/run_id,
instance_id и URL только собственного экземпляра; дополнительно launcher_engine=rust.
Журнал `logs/native-runtime-lifecycle.jsonl`, ротация 1 МиБ + 3 копии. Ключи,
содержимое документов, пользовательские имена моделей в lifecycle не пишутся.

Сборка: `tools/build_native_runtime.py --offline --output NEW_DIR`. Сверяются
SHA binary, digest исходников/lock/version и remap путей. Пакетировщик принимает
`--native-runtime FILE`, включает реальные Rust-лицензии. Старые assets не
перезаписываются. Development-инструменты могут оставаться Python; продуктовая
основа переносится отдельно от сборки.

Для будущего API фиксируется исходный контракт 265 method/path пар и схем:
`tools/native_api_contract.py`, `docs/generated/native-api-baseline.json`.
Снятие выполняется в отдельном временном состоянии без секретов/моделей пользователя;
OpenAPI-проверка не заменяет поведенческие тесты сохранённых сценариев.

Кандидат 776: `--native-api` запускает также `native/api/les-api.exe`, прежний API
получает отдельный внутренний порт и имя `legacy_api`. Статус содержит
`api_native=true`, `api_pid` Rust и `legacy_api_pid`; оба процесса наблюдаются и
завершаются при закрытии. Публичные URL остаются адресами Rust API.
