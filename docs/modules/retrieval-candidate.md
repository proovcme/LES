# Независимый кандидат поиска и контекста

Код написан самостоятельно; реализации Legion не переносились. Кандидат не
подключён к обработчику чата, не устанавливает модели и не мигрирует основной индекс.

## Компоненты

- `backend/inference/bm25_weighted.py`: документные веса
  `(k1+1)*tf / (tf + k1*(1-b+b*length/average_length))`; k1=1.2, b=0.75.
  Вопрос имеет единичные веса уникальных термов. IDF применяет Qdrant ровно один раз.
  Средняя длина измеряется по замороженному корпусу. Прежний TF-код остаётся
  неизменным по поведению, его название не является доказательством BM25.
- `backend/retrieval_candidate.py`: native dense+sparse RRF на изолированной
  коллекции `les_trial_*`; необязательный явно переданный реранкер. Он обязан
  вернуть перестановку исходных ID. Ошибка этапа не маскируется успехом.
  Родитель читается из индекса с фильтром dataset_id + file_name + parent_id,
  с пагинацией и исключением навигационных узлов. Количество фрагментов ограничено;
  превышение лимита является ошибкой, не «полным разделом».
- `proxy/services/section_evidence_candidate.py`: сохраняет поисковые попадания
  прежде чем добавлять соседей; один родитель читается один раз. Общий бюджет
  охватывает сериализованный контекст, включая идентификаторы и страницы.
  Каждый фрагмент сохраняет собственную цитату. Непоместившиеся части не обрезаются
  молча; `complete=false` означает неполный индексированный родитель.
- `tools/evaluate_retrieval_candidate.py`: сравнение на собственном нативном
  Qdrant, в новом каталоге. Исходные dense-векторы и вопросы совпадают; сравниваются
  только sparse-веса. Выходной каталог должен отсутствовать. Процесс останавливается
  и при исключении. Никаких записей в исходный индекс или исходные документы.

## Запуск

```text
python tools/evaluate_retrieval_candidate.py --snapshot snapshot.json --queries queries.json --cases cases.json --output trial-new --qdrant-exe PATH_TO_QDRANT
```

Snapshot: `embedding_fingerprint`, `points` с `id`, `vector.dense`, `payload`.
Query export: такой же fingerprint и `queries` с `id`, `question`, `dense`,
`dataset_ids`. Cases: список `id`, `question`, `gold_groups`; каждая группа содержит
`support[].point_id`, необязательный `anchor`. Совпадение точного ID или якоря
в поисковом фрагменте засчитывает группу. Доли считаются отдельно для top-5 и top-10.
Пустые gold_groups не считаются успешным поиском; они требуют отдельной проверки отказа модели.

Текущий запуск использует консервативную оценку токенов из общего governor, а не
точный токенизатор генератора. Полный запрос с историей и резервом ответа остаётся
за основным governor; бюджет кандидата предназначен только для доказательств.

## Граница приёмки

Это контролируемое сравнение весов внутри одинакового native RRF. Оно не сравнивает
весь установленный конвейер с иерархическими маршрутами, FTS и дополнительными
правилами. Иерархия рабочего приложения не изменялась. `complete` означает полноту
текущего индексированного родителя, не доказанную полноту OCR или всего оригинала.

Для рабочего включения нужен версионированный sparse-контракт и явная миграция
с сохранением dense-векторов, согласованным обновлением индекса и откатом.
Автоматически подмешивать новые веса к старым запрещено.
