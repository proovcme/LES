# Отбор контекста после дочитывания

Кандидат 877, рабочая установка не переключена. Результат пользовательской
проверки записывается отдельно в приёмке; описание алгоритма её не заменяет.

## Единственный владелец отбора

`core/src/context_selection.rs` выбирает целые единицы по всему переданному
пулу. Rust API и изолированный Swiftide Query вызывают одну реализацию.
Она не ищет новые файлы, не меняет RRF или индекс, не выбирает модель и
не утверждает, что в корпусе больше нет ответа.

Порядок автоматического пути:

1. Dense + BM25 + RRF возвращают ограниченный пул совпадений.
2. До 64 зарегистрированных совпадений и их индексированных родителей
   рассматриваются при одном поколении. Общий селектор формирует план чтения
   в заданном бюджете, без отдельного лимита по файлу. Он сохраняет исходные
   ранги и не требует распознать все найденные файлы до определения нужных.
3. Запланированный Word перечитывается из оригинала и получает структурные единицы;
   плавающие объекты отделены от тела/ячеек. Найденный индексный OCR PDF
   обновляется каноническим физическим читателем, без подстановки старого
   текста при отказе. PDF-представления проверяются по хешу и адресу страницы.
4. Совпадающие текст и заголовок объединяются для контекста. Внутренний список
   происхождений сохраняется; ограниченный ответ явно обозначает усечение
   подробных дублей. Разные файлы и редакции не объявляются одной
   редакцией. Числа, регистр единиц, знаки и границы строк не исправляются
   ради объединения. Различающиеся таблицы остаются самостоятельными.
5. Отбор учитывает исходный ранг, лексическое соответствие вопросу, вклад
   заголовка раздела, новые термины и повторяемость уже выбранного текста.
   Использован бюджетный вариант maximal marginal relevance: предельная
   полезность делится на корень стоимости блока, чтобы один длинный родитель
   не занял всё окно только из-за большего числа совпавших слов.
   Ранг найденного Word-фрагмента не копируется во все абзацы документа.
   Совместимая индексированная структурная единица сохраняет свой ранг;
   дополнительные единицы имеют `rank=null` и оцениваются по содержанию.
   Они не получают фиктивный dense-голос только из-за принадлежности файлу.
6. В модель поступают целые блоки, их заголовки и проверяемые номера источников.
   Общий упаковщик всё ещё учитывает фактический запрос, историю, схемы,
   резерв генерации и размеры полного конверта.

Для контекстного сопоставления используется уже согласованный Snowball v3
из имеющейся зависимости. Это отдельное преобразование текста кандидатов и
вопроса; postings, версия анализатора рабочего индекса и dense-векторы не
пересчитываются. Имена файлов не добавляют текстовую релевантность.
Без лексического сигнала сохраняется порядок поиска: непохожесть двух текстов
сама по себе не доказывает полезность второго текста.

## Что не объединяется с этим путём

Явные `read_source` и страницы `search_sources` по-прежнему возвращают
непрерывный префикс исходного потока. Контекстная дедупликация и изменение
порядка не применяются к курсору. Два одинаковых текста на разных позициях
такого чтения остаются двумя позициями; смещения и окончания не теряются.

Полная передача родителя не равна полному допуску его текста. Частичный
документ не получает признак полного. Сохранённые совпадающие происхождения
не доказывают равенства всех остальных страниц документов и не позволяют
объявлять совпадение ПД и РД.

## Данные и стоимость

Вход: исходный вопрос, текст, заголовок, зарегистрированный источник,
идентификатор единицы и ранг. Выход: выбранные единицы, совпадающие
происхождения и диагностика числа кандидатов/уникальных единиц, бюджета
и покрытия терминов. Покрытие — диагностическое, не вероятность истины.

Стоимость общего селектора учитывает текст, видимый заголовок, основной
источник и резерв оформления. Список совпадающих происхождений хранится
отдельно от повторяемого текста; его размер отражается в диагностике.
Финальные JSON/токенные ограничения применяются независимо и не отключены.
Для API происхождения дополнительно разрешаются через каталог с проверкой
доступа и SHA-256, прежде чем попадут в карту источников.

Новые предметные правила, списки имён файлов, эталонные ответы, новые модели
или загрузки зависимостей в этот путь не добавлены.

## Навигация и ограничение эксперимента

`context_catalog` строит одну карточку на физический документ до отбора
фрагментов, сохраняя путь и несколько заголовков. Ограничение — 64 документа;
карточки имеют `evidence_admissible=false`. Рендерер чата резервирует
идентификаторы перед сокращением длинных подписей: поздний файл не исчезает
из-за длины имени раннего. CPU-отбор выполняется вне потока API.

Изолированный стенд может передать `preferred_groups` (до четырёх известных
документов); неизвестный/пустой выбор не расширяется обратно до всех.
Это не включённый в приложении выбор файлов Qwen и не принятый обзорный синтез.
Окно документа ограничено 128 единицами и 200 тысячами символов. Если документ
не помещается, окно явно частичное; оно не доказывает последовательное чтение
полного оригинала. Для точного обхода используется явный читатель с курсором.

MCP использует [общий договор чтения](native-source-mcp.md), без дополнительной
модели ответов между источниками и внешним клиентом.

С build 877 этот автоматический путь доступен без ответной модели через
`search_sources(view=context)`. Общий ограничитель исходного пула учитывает
8 МиБ текста и 16 384 единицы одновременно; короткие абзацы Word не
приравниваются к крупным страницам по одному лишь числу элементов.

Внешний ответ MCP/API ограничивается транспортным конвертом; внутренний
prefetch чата сохраняет кандидатный каталог и помещающиеся страницы до
модельного упаковщика. Это разные бюджеты доставки одного читателя.
Переполнение предварительного расчёта места для следующего чтения проходит
тот же путь освобождения схем инструментов, что переполнение всего хода:
прочитанные доказательства не обрезаются и не заменяются пустым ответом.
Допуск чтения сохраняет место для следующего вызова инструментов, а не
занимает всё возможное окно финального ответа. В модельной схеме читателей
типы и ограничения сохранены; повторяющиеся описания полей убраны, правила
продолжения изложены один раз в кратком описании инструмента. Полные схемы
API/MCP сохранены. Фактический пакет модели считает все передаваемые схемы.
