# Память исполнения и задания — установленный локальный 784

Установлен и проверен локальный 784. [Приёмка](../acceptance/runtime-memory-784.md).
Пороги RAM/commit, модельные назначения и исходные файлы не меняются.

`core/src/memory.rs` выбирает очистку по фактической свободной RAM. Освобождение
форматного процесса проходит через try_lock: работающий запрос и очередь ожидающих
не отменяются. Простаивающий процесс закрывается вместе с его потомками.
На Windows HeapOptimizeResources освобождает неиспользуемые LFH-кэши; живые страницы
working set не вытесняются ради красивого счётчика. [Контракт Windows](https://learn.microsoft.com/en-us/windows/win32/api/heapapi/nf-heapapi-heapsetinformation).
`backend/runtime_memory.py` собирает недостижимые Python-объекты перед измерением,
вызывает native reclaim и записывает before/after. Временный Qdrant HTTP-пул
закрывается на успехе и ошибке. Полные результаты файла по-прежнему строятся Python;
это не перенос всей индексации и не обещание фиксированного RSS.

После batch очистка выполняется до post-memory guard; завершение/ошибка/отмена
очереди также освобождают простаивающие ресурсы. Старый final_unload остаётся None:
очередь не выгружает произвольные модели. Новая диагностика — memory_cleanup.

`request_memory_service` запоминает фактически вызванную модель в области текущего
asyncio Task. Вложенная фоновая задача имеет свой жизненный цикл. После ответа
только при нехватке RAM и только для явно назначенной loopback Ollama без auth
запрашивается keep_alive=0 для использованного model_id. Назначение сохраняется;
следующий вопрос загрузит ту же модель. Штатный semaphore исключает выгрузку во
время другого запроса Леса. Удалённые, произвольные OpenAI API, другие model_id,
демон Ollama и чужие процессы не затрагиваются. HTTP ограничен по времени,
редиректы/прокси окружения выключены; ошибка очистки не уничтожает готовый ответ.
Проверка допуска следующего ответа остаётся прежней и использует живые метрики.
Освобождение после каждого завершённого модельного turn также защищает следующий
turn harness. Для метрик используются те же десятичные GB и chat_min_free_gb,
что у допуска: значения GiB и GB не смешиваются.

Если до первого ответа RAM всё ещё ниже порога и активных заданий нет,
`chat_prepare` может освободить модель явно назначенной роли ANSWER, оставшуюся
в Ollama от прошлого запуска. Ревизия проходит штатный resolver с CHAT_COMPLETIONS;
до него отсекаются remote/custom/auth URL. Занятый слот запрещает выгрузку.
Нет обхода capability/disabled-проверок и подмены роли. После очистки весь допуск
проверяется снова. Ошибка подготовки сохраняет исходный понятный отказ.
[Протокол освобождения](https://docs.ollama.com/api/generate).

`/api/indexing-mode` и `/api/status` используют один живой снимок для допуска и
состояния RAM. Устаревшая телеметрия не может отдельно показывать ложную паузу
или разрешение. При ошибке системного замера сохраняется прежняя защитная
телеметрия; глобальный кэш не переписывается. Порог по умолчанию — прежние
4 десятичных GB, дополнительного порога удержания модели нет.

`embedding_residency` связывает фактически выполненные запросы эмбеддингов с
областью одного parse-вызова, включая asyncio.to_thread. Только использованные
loopback Ollama с подтверждённым native_embedding_v1 и без auth освобождаются
через пустой /api/embed с keep_alive=0 после окончания порции. Внутри порции
модель переиспользуется; cache-only вызов ничего не выгружает. Ошибка очистки
не меняет результат публикации. HTTP освобождения ограничен восемью секундами.
Ожидание unmap ограничено пятью секундами: требуется не менее секунды после
подтверждения и четыре последовательных замера не ниже прежнего порога. Один
краткий переход через порог недостаточен. При раннем вопросе дополнительная
очистка ожидает до двух секунд; окончательный допуск проверяется снова, порог
не снижается. Ошибка HTTP также допускает ограниченное ожидание: сервер мог
уже начать освобождение до разрыва соединения. Отмена asyncio.to_thread не означает завершения рабочего
потока: при такой отмене модель из-под него не выгружается.
[Протокол embeddings](https://docs.ollama.com/api/embed).


`core/src/catalog/job_store.rs` владеет прежней таблицей jobs в les_meta.db:
инициализация, create/get/list/active, атомарные update и recovery. Запись —
BEGIN IMMEDIATE, synchronous=FULL, WAL, busy timeout 30 с. Нативная политика
переходов не даёт запоздалому callback оживить завершённое задание. Ошибка в
середине восстановления откатывает всю транзакцию, прежние строки не заменяются.
Результат задания передаётся через ABI как непреобразованный JSON-текст,
сохраняя большие целые числа, Unicode и точность прежнего codec.
Python JobService — фасад/codec без SQL; прежние store/policy находятся только в
`tests/oracles`. Оркестрация scheduler, память job_tracker и HTTP jobs ещё Python:
полный перенос очереди/исполнителя этим этапом не объявляется.
