# Как ЛЕС считает светильники по DWG

26 ноября 2026 · кандидат 948

Папку с чертежами можно подключить как датасет в ЛЕС и спросить «Сколько светильников каждого типа на плане?» или «Посчитай мощность освещения в DWG». Чат ЛЕС и MCP используют одну операцию над индексом выбранного датасета.

## Что лежит в чертеже

На контрольном плане светильник задан вставкой блока. Имя блока обозначает тип. Слой помогает определить назначение. Атрибут `POWER_W` хранит мощность одной позиции в ваттах. В примечании на листе `02_EO` автор чертежа отдельно указал итог по рабочим и аварийным светильникам.

При индексации ЛЕС сохраняет два вида данных. Тексты, слои, блоки и листы дают поисковые фрагменты. Для каждой прямой вставки в пространстве модели дополнительно сохраняется структурированная запись с именем блока, слоем, атрибутами, количеством и handle. Запись привязана к датасету и SHA-256 исходного чертежа. Сам DWG остаётся во внешней папке.

## Как получается ведомость

ЛЕС находит корневую запись пространства модели по связке блока и раскладки. Подсчёт берёт вставки, для которых этот корень указан владельцем. Для прямоугольного массива количество равно произведению строк и столбцов. Определения блоков, вложенные вставки, объекты пространства листа и видовые экраны в подсчёт не входят. Так один светильник, который виден на нескольких листах, учитывается один раз.

Для запроса о светильниках ЛЕС выбирает вставки по обозначениям освещения в именах блоков и слоёв. На контрольном плане это слои `EO-LIGHT` и `EO-EMERG`. В MCP также доступны точные фильтры по имени блока и слою. Строки группируются по чертежу, имени блока, марке и слою. К каждой строке прилагается источник с handle одной вставки из группы.

Сумма строится по числовым значениям `POWER_W`. Явно записанные киловатты переводятся в ватты. Без этого атрибута либо при конфликтующих или нечитаемых значениях позиция идёт в количество, а её мощность отмечается как неизвестная. При запросе ведомости ЛЕС обходит все подходящие структурированные записи выбранной ревизии в пределах лимитов операции. Языковая модель для подсчёта не вызывается.

Сумма по 20 рабочим светильникам составила 576 Вт, по четырём аварийным 12 Вт. Значения совпали с итогом на листе `02_EO`, handle примечания `48F`.

## Что проверили в ЛЕС

Подключили внешнюю папку в отдельном профиле Windows. Индекс получил 1 079 точек, из них 58 содержали записи о прямых вставках. Чат и локальный MCP вернули одну ведомость с четырьмя строками и итогом 588 Вт, пока исходный файл был заблокирован для чтения. Отдельный запрос к поиску нашёл текст примечания с handle `48F`. Контрольная ведомость RVT по тому же профилю по-прежнему содержала девять кранов. После возврата к сборке 947 контрольный поиск по обоим датасетам сработал.

Прогон выполнен локальным кандидатом с изолированным профилем. Отдельную визуальную проверку окна провести не удалось из-за отказа в доступе к Edge. Полный установщик на этом этапе не проверялся.

## Проверка на рабочем комплекте ЭО

Читатель разобрал 22 DWG комплекта внутреннего электроосвещения. Три из них содержат планы расстановки. Остальные включают схемы и общие данные. В изолированном датасете ЛЕС проиндексировал 69 416 фрагментов DWG и спецификацию Excel. Чат и локальный MCP вернули 1 674 прямые вставки на слоях освещения в 67 группах. Поиск по точному названию каждого плана нашёл его заголовок первым. Для этого контрольного прогона использовался тестовый эмбеддер.

| Отметка плана | Прямые вставки в Model | Попали в фильтр освещения | Из них с заполненным №СП |
|---|---:|---:|---:|
| 0.000 | 762 | 679 | 304 |
| +4.500 | 794 | 658 | 485 |
| +9.000 | 385 | 337 | 302 |
| **Всего** | **1 941** | **1 674** | **1 091** |

Вставки на слоях освещения дают проверяемый подсчёт условных обозначений. Чтобы он стал ведомостью оборудования, нужно связать обозначения с подписями на планах и спецификацией. Например, блок `OWS_R 4x18W` на рабочем и аварийном слоях встречается 588 и 127 раз. У этих групп атрибут `№СП` равен `3` и `3А`. В Excel и PDF те же количества указаны у светодиодных OPTIMA.PRS на позициях 4 и 5. Обе позиции по 29 Вт. На самих планах есть выноски с названиями OPTIMA.PRS и OPTIMA.PRS EM. Совпадение количества и подписей даёт основание проверить связь по чертежу. Подстановка по имени блока или номеру позиции дала бы другой результат.

Ещё один контрольный пример есть на плане 0.000. Три выноски указывают 70, 70 и 98 светильников HB LED 150. Их сумма совпадает с позицией 20 спецификации (238 шт., 144 Вт). Для таких выносок полезно хранить собственные количества и ссылки на handle, чтобы сверять их с прямым подсчётом и не прибавлять второй раз.

На трёх планах атрибут `POWER_W` отсутствует. Поэтому расчёт 948 оставляет мощность неизвестной. Для ведомости по комплекту нужно проверить сопоставление обозначений с выносками и строками спецификации. По каждой строке тогда можно показать источник количества отдельно от источника марки и мощности.

### Сверка 26 позиций светотехнической продукции

Все 26 строк Excel, 303 надписи на планах и четыре контрольные группы вставок сверены через API ЛЕС и локальный MCP. Общая выборка `MTEXT` не вместила все нужные надписи. Оставшиеся записи дочитаны по названию и handle.

## Границы результата

Пока ведомость отражает прямые вставки в пространстве модели, которые вернул читатель. Условные обозначения из линий, содержимое внешних ссылок и вложенные вставки требуют отдельного учёта. Если в пространстве модели блоками нарисована легенда, её вставки тоже попадут под подходящий фильтр. При другой системе обозначений нужны известные имена блоков или слоёв. Для DWG из старого индекса нужно заново проиндексировать исходник, чтобы появились структурированные записи.

## Сверка в 949

В 949 фраза «Сверь спецификацию с DWG» сама запускала расчёт. Через MCP расчёт был доступен по `model_inventory` с `mode: "dwg_spec"`. Если книг несколько, нужен `spec_doc_id`. Параметры `spec_sheet`, `row_start` и `row_end` закрепляют диапазон.

Операция использует существующий индекс. По каждой строке она показывает количество Excel, явную сумму выносок, количество сопоставленных вставок и ссылки на источники. Суммы хранятся раздельно. У возможных связей указаны имя блока, слой и сохранённая позиция. Количество по нагрузкам электрических схем в этот расчёт не входит.

На проверочном комплекте весь раздел Excel содержит 28 позиций. Ручная сверка выше охватывает первые 26, строки 37–62. Автоматическая сверка включает две позиции из продолжения таблицы, драйвер и ящик с трансформатором.

Автоматическая сверка нашла три совпадения по явным количествам, три возможные связи и шесть расхождений по прочитанным данным. У трёх позиций нашлись только подписи без количества. Для 13 позиций количество по чертежу осталось неподтверждённым. Три совпадения и 303 сопоставленные надписи воспроизвели контроль ручной сверки.

API, чат и локальный MCP проверены на копии индекса 948, с заблокированными для чтения оригиналами трёх планов и Excel. Проверены ссылки на строки книги и объекты DWG, продолжение в MCP с той же редакцией индекса и диапазон из 26 строк. После возврата к 948 прежний подсчёт снова вернул 1 674 вставки.

## Как запускается сверка с 950

Выберите датасет с DWG и Excel и спросите, например, «Где расходятся данные по светильникам между планами и ведомостью?». Если модель поддерживает инструменты, ЛЕС передаёт ей вопрос, фрагменты из индекса и описание `model_inventory`. Модель может вызвать `dwg_spec`, например с указанием книги и диапазона, или ответить по найденным фрагментам. Правило запуска по фразе из 949 удалено. В MCP используется тот же расчёт с явным вызовом `model_inventory`.

На копии рабочего индекса тестовый ответчик сначала получил прежнюю фразу и вернул ответ без вызова. Ведомость в этом запросе не строилась. Затем на вопрос выше ответчик вызвал `model_inventory` и получил 28 позиций и шесть расхождений по прочитанным данным. По первой позиции в ответ попали 53 шт. по выноскам против 61 шт. в Excel, со ссылками на строку книги и объект DWG. MCP по тем же параметрам вернул тот же структурированный результат.
