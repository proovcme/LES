# LES Light — инструкции для разработки

Самостоятельное публичное приложение: чат, проекты, документы, память, скиллы,
MCP и поиск по источникам. Версия продукта 0.1.0. Основная платформа — Windows.
Это самостоятельный репозиторий, не worktree большого ЛЕС.

Проектный навык разработки: [skills/les-light/SKILL.md](skills/les-light/SKILL.md).
Применяйте его при работе над Light; не включайте в промпты модели приложения.
Пересборка продукта: [docs/LIGHT_ARCHITECTURE.md](docs/LIGHT_ARCHITECTURE.md).
Читайте docs/SEPARATION.md, затем docs/MODULE_INDEX.md и код нужного модуля.
Унаследованные документы большого ЛЕС не задают правила запуска этой копии.
Перед любой правкой интерфейса обязательно прочитайте
[docs/LIGHT_PRODUCT_CONTRACT.md](docs/LIGHT_PRODUCT_CONTRACT.md), затем
[docs/UI_CONTINUITY.md](docs/UI_CONTINUITY.md): принятый дизайн, границы изменений
и незакрытые дефекты. Отчёты в docs/acceptance не заменяют этот договор.

## Обязательные границы
- Нет сметного сценария в пользовательском интерфейсе Light.
- Сметный модуль физически удалён из репозитория Light в build 738. Не
  восстанавливать его из большого ЛЕС, не добавлять `smeta`/ЛСР/РИМ/ГЭСН
  маршруты, команды, память или файлы в пакет. Внешние сметные данные — только
  через явное подключение MCP пользователем.
- Сметные/Gemini-ветви полного ЛЕС не должны становиться настройками,
  промптами или скрытыми маршрутами Light. Внешний сметный сервер — только
  через явно выбранные MCP-инструменты чтения.
- Собственный нативный Qdrant и отдельный каталог состояния; Docker не нужен.
- Только явные назначения моделей для чата и поиска. Нет скрытого fallback.
- Целевые подключения: локальная Ollama и совместимый OpenAI API.
- Не отправлять документы/письма и не менять модели без действия пользователя.
- Outlook — только чтение; не отправлять, не удалять, не менять письма.
- Не менять решения модели скрытыми предметными эвристиками.
- Не читать секреты, не публиковать личные адреса, файлы и названия машин.
- Не устанавливать зависимости без согласования; использовать uv.lock.
- Не публиковать и не настраивать remote без отдельной команды пользователя.

## Проверка
Для изменений нужны регрессионные тесты, make verify, make test и проверка
затронутого интерфейса. Не объявлять установленным то, что проверено в исходниках.
Обновляйте документацию и config/version.json вместе с изменениями.
Сборка: tools/build_light_package.py; установщик: installers/windows/light/setup.nsi.
Текущее состояние переноса и ограничения указаны в docs/SEPARATION.md.

Обновления выполняются по цепочке baseline → candidate → rollback.
Необходимо не объявлять исправление готовым до installed user journey;
тесты исходников не заменяют проверку установленного приложения.

## Не повторять ошибки приёмки
- Палитра и отступы не равны переносу макета. Описывать фактическую компоновку.
- HTTP 200 и зелёные тесты не доказывают визуальную геометрию, резкость или все клики.
- В карточках моделей показывать model_id и сервис; display_name сохранять как
  пользовательское имя в подробностях. Не выводить preset_id как «Источник».
- Не исправлять ложную готовность переименованием. INDEXED без фрагментов —
  открытая проблема; требуется сверка документов, индекса и пути поиска.
- Не добавлять очередной CSS override без проверки старых width/max-width,
  специфичности и мобильных правил. Править существующий общий UI kit.
- Не менять DPI, масштаб Windows или WebView на основании одного скриншота.
- Проверять интерфейс в браузере при разрешённом Computer Use. Отдельно отмечать
  непроверенные сценарии нативного окна, экранного диктора и чистой Windows.
- Перед перезапуском пользовательского окна сохранить возможность не потерять
  черновик/ответ: дождаться закрытия окна пользователем либо его явного согласия
  на прерывание. Не убивать процессы по широкому имени.
- Изменения документировать в том же наборе правок; различать исходники,
  установленный локальный патч, полный установщик и публичный релиз.
